== How status works

Every spec under `docs/specs/` carries its own status and a progress
checklist, one line per acceptance gate. A status is only as good as its
evidence, so the rules are enforced by `dq/tests/test_specs_contract.py`.

[cols="2,5",options="header"]
|===
| Status | Meaning

| Proposed
| Written and awaiting acceptance.

| Accepted
| Scope frozen and scheduled in a milestone.

| In Progress
| At least one acceptance gate is met.

| Verified
| Every gate is met, each with an `evidence:` citation, and CI is green on
  the pull request that carries the spec.

| Released
| Included in a tagged release named on the status line.

| Blocked
| Cannot proceed; the status line names the blocker.

| Deferred
| Accepted but not scheduled; the status line says why.

| Superseded / Rejected
| Replaced by another spec, or declined; the status line says why.
|===

A status may not skip `Verified`. A gate that cannot be evidenced by a test,
a command, or an observed CI run is not a gate.

== Milestones

[cols="1,6",options="header"]
|===
| | Goal

| M0
| **Trust the baseline.** Specs are tracked and CI tells the truth.

| M1
| **Authoring and extensibility.** Rule packs in any format, an engine SDK,
  and severity that means something at the gate.

| M2
| **Evidence plane.** Any database as the durable sink, results from other
  tools in one stream, and runs that can be observed.

| M3
| **Compute reach.** Portable plans without Spark: Arrow and SQL, plus the
  pandera and Soda engines.

| M4
| **Runtime intelligence.** Profiling, history and trends, row quarantine,
  and streaming.

| M5
| **Platform and distribution.** Signed releases, the expectation compiler,
  and a container image.
|===

== Historical proposals: triage

Four documents describe the framework as it was before the modernization
sequence: `future-enhancements.adoc`, `architecture-improvements.adoc`,
`performance-optimization.adoc`, and `technical-debt-analysis.adoc`, indexed
by `improvements-index.adoc`. They are kept as a record of how the
architecture was reasoned about. They are not a plan. Every proposal they
make has one disposition here.

[cols="3,2,5",options="header"]
|===
| Proposal | Disposition | Where, or why not

| Remove executable configuration (`eval`)
| Shipped
| Modernization unit U1; assertion expressions are parsed, never evaluated.

| SQL injection hardening
| Shipped
| U1 and U4; identifiers are validated value objects (`dq.identifiers`).

| Replace driver `collect()`
| Shipped
| U5; businessrules returns bounded per-column summaries.

| Input validation
| Shipped
| U1 through U4; fail-closed boundaries with framework exceptions.

| Inheritance hierarchy
| Shipped
| ADR-012; engines compose the shared scaffold instead of inheriting.

| Error handling
| Shipped
| Fail-closed boundaries and the error catalog (SPEC-004).

| Configuration validation
| SPEC-010
| `dq-validate` exists; typed snapshots and more formats arrive with SPEC-010.

| Caching system
| Shipped in part
| Engines cache their construction once (ADR-012). A general caching layer is
  not planned: there is no measured need.

| Plugin architecture
| Shipped
| ADR-012: engine contract, registry, entry points.

| Parallel processing
| Deferred
| Each engine's checks already run as distributed Spark jobs. Python-level
  threading adds failure modes without a measured gain; revisit with a
  benchmark.

| Real-time monitoring
| SPEC-014
| Run observability. A monitoring platform is out of scope (ADR-007).

| REST API
| Rejected
| ADR-001: ports are Python interfaces, not network services.

| Multi-environment configuration
| SPEC-010
| Overlays through includes and environment substitution.

| Typed configuration schema
| SPEC-010
| Plain frozen dataclasses; a validation framework is not pulled in.

| Structured logging
| SPEC-014
| Run context on every line; optional JSON output.

| Circuit breaker
| Rejected
| A batch library that already fails closed has nothing to trip.

| Query optimization
| Shipped
| U5; one shared aggregate per dataset.

| Property-based testing
| SPEC-011
| Hypothesis over the pure kernel functions.

| Performance scaling tests
| Deferred
| CI cost policy: scale benchmarks run on a scheduled or manual runner.

| Streaming data quality
| SPEC-022
| Per micro-batch validation on the shared run core.

| Alerting system
| SPEC-012, SPEC-020
| Notifier conformance, then trend policies on evidence history.

| Data quality dashboards
| Rejected
| ADR-007: a dashboard company is a different company.

| ML anomaly detection
| Deferred
| ADR-007 keeps machine learning out of the kernel; SPEC-020 ships statistical
  detectors, and a learned detector would be an optional later pack.

| AI-assisted rule optimization
| Deferred
| Not prescribed. SPEC-019 ships deterministic rule suggestion.

| Layered microkernel and domain services
| Shipped in substance
| The plugin layer is ADR-012; the rule engine and orchestration are the run
  core (ADR-014).

| Event bus
| SPEC-014
| An observer port replaces an in-process event bus.

| Partition optimization
| Deployment
| Storage tuning belongs to deployment configuration (U6).

| Predicate pushdown
| Deployment
| A Spark engine concern, not a framework one.

| Test coverage target (85%)
| Exceeded
| 91% line and 89% branch coverage at the time of writing.

| Code duplication
| Shipped
| Zero clones at a 120-token window.

| Control plane and marketplace offers (MVP-2)
| SPEC-005
| Deferred: the control plane moved to a closed, now archived, repository.

| Coexistence guides for Lakehouse Monitoring and Glue DQ
| Deferred
| Follows SPEC-013 and SPEC-023, which supply the technical content.
|===

== Not prescribed

Candidates that are consistent with the architecture but were never asked
for. They are listed so that promoting one is a deliberate decision.

* An MCP tool surface exposing validate, profile, and run to coding agents.
* Importing an ODCS data contract as a rule pack.
* E-mail and SMS notifiers.
* A Helm chart for running validation jobs on Kubernetes.

== Reading a spec

Each spec states a purpose, what is in and out of scope, its contracts, and
its acceptance gates. The `Progress` section has one line per gate; a
checked line cites its evidence. The header names the milestone and any
dependency or gate.
