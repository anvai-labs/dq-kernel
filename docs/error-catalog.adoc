= Error catalog
:toc:
:sectlinks.

Status: Maintained by contract test (U7/TD-PROD-5) +
Date: 2026-09-21

This catalog maps every fail-closed boundary to its cause and remediation.
The framework raises 308 raise sites across the modules below; the contract
test `dq/tests/test_error_catalog.py` keeps module coverage and exception
types in sync with the code. Spec: SPEC-004.

Every error derives from `DQFrameworkError`. `ConfigurationError` and
`IdentifierError` mean "fix the configuration"; `ValidationError` means
"the data or evidence failed validation — this is a quality signal, not a
bug"; `ValueError` marks legacy engine boundaries; `DataFrameNotFoundError`
means the referenced table could not be resolved; `RepositoryError` means
the evidence store refused an unsafe write; `HarvestError` is a
`ConfigurationError` raised when another tool's results cannot be imported.

== dq/notifier.py

*Content:* 5 `ConfigurationError` sites.

* Cause: an HTTP notifier (`webhook`, `slack`, `teams`) is missing a
  `url_env` key naming the environment variable that holds its URL, that
  environment variable is absent at construction time or does not hold an
  `http` or `https` URL, an HTTP notifier is configured with fewer than one
  attempt, or the notifier `type` is not one of `logging`, `memory`,
  `webhook`, `slack` or `teams`.
* Fix: set the environment variable to an `http` or `https` URL and ensure
  the configuration names it via `url_env`; use a supported notifier type.

== dq/plan.py

*Content:* 31 `ConfigurationError` + 6 `ValidationError` sites.

* Cause: malformed kernel construction — identifiers, digests, predicates,
  metric/rule structure, semantic-version mixing, capability mismatches,
  metric-supply mismatches.
* Fix: construct plans only from `dq.plan` value objects; supply exactly the
  deduplicated metric set `plan.metrics` requests, with counts as unsigned
  ints and range bounds as exact `Fraction`s.

== dq/portable_config.py

*Content:* 26 `ConfigurationError` sites.

* Cause: legacy checks outside the translatable subset, malformed fields,
  or disabled/missing bounds.
* Fix: restrict the check to `isComplete`, single-comparison
  `hasCompleteness`, integer-comparison `hasSize`, `DistinctnessByGroup`,
  `isNonNegative`, or `isInRange`; anything else stays on the legacy engine
  path.

== dq/outcomes.py

*Content:* 15 `ValidationError` sites.

* Cause: outcome evidence violated the strict JSON boundary (size, depth,
  nodes, bytes, UTF-8, key types, boolean success) or the batch shape.
* Fix: reduce diagnostic payloads or split the batch; results are never
  truncated.

== dq/sinks.py

*Content:* 6 `ConfigurationError` + 1 `RepositoryError` sites.

* Cause: repository configuration missing dataset/format/targets, malformed
  table names, or a duplicate idempotent write.
* Fix: provide dataset, whitelisted format, and at least one target; a
  duplicate key means the caller is reusing an execution key.

== dq/sqlalchemy_sink.py

*Content:* 6 `ConfigurationError` + 4 `RepositoryError` sites.

* Cause: the durable sink was given something other than a SQLAlchemy
  `Engine` or `Connection` -- a DB-API connect callable, as before SPEC-007;
  the database location names a driver or a dialect that is not installed;
  the location's environment variable is absent; the dataset name is missing;
  retention is not explicitly configured; the evidence tables are absent; or
  a database failure occurred during the schema check.
* Fix: build the engine with `sqlalchemy.create_engine(url)` and install the
  driver the URL names (`pip install "psycopg[binary]"` for
  `postgresql+psycopg://`), export the location variable (default
  `DQ_POSTGRES_DSN`), set `dataset`, configure `retention_days`, and apply
  `ddl_statements()` before querying evidence. A failure while writing
  surfaces as the database driver's own exception.

== dq/spark_adapter.py

*Content:* 2 `ConfigurationError` sites.

* Cause: dataset bindings are not a mapping, or a bound object is not a
  Spark DataFrame. Everything else a plan can get wrong -- bindings that do
  not exactly match the plan's datasets, a bare plan handed to
  `execute_envelope`, a missing or ambiguous column, an infinite bound -- is
  refused by `dq/compute_support.py`, which every adapter shares.
* Fix: pass a mapping of dataset names to DataFrames.

== dq/arrow_adapter.py

*Content:* 3 `ConfigurationError` sites.

The Arrow compute adapter (SPEC-015): portable plans over Arrow tables.

* Cause: dataset bindings are not a mapping, do not name exactly the plan's
  datasets, or hold something Arrow cannot read -- not a pyarrow table, a
  record batch, an object exporting Arrow's stream interface (Polars,
  DataFusion, pandas), or a Spark DataFrame. Or Arrow has no kernel for what
  a plan asks of a column: a list or a struct has no distinct count and no
  bound, and the message names the dataset, the column and the metric.
* Fix: bind each dataset to an Arrow table or to an object that exports one;
  for a nested column, measure a column that holds values, or encode it
  first. The refusals every adapter shares are listed under
  `dq/compute_support.py`. Without pyarrow installed the adapter names the
  `arrow` extra instead, before any dataset is read.

== dq/sql_adapter.py

*Content:* 12 `ConfigurationError` sites.

The SQL compute adapter (SPEC-016): portable plans compiled to one aggregate
statement per dataset, run on an SQLAlchemy bind. DuckDB is the certified
lane.

* Cause: dataset bindings are not a mapping, do not name exactly the plan's
  datasets, or a binding is not a `SqlDataset` -- a table whose columns
  declare their types and a bind that is an `Engine`, a `Connection`, or
  something with a dialect and an execute. Or the bind's dialect is one the
  adapter does not know (it knows DuckDB and PostgreSQL), so nothing is
  asked of it. Or, for each metric on its own, the column it names cannot
  be measured that way: a type the adapter does not recognise (JSON, an
  array, a struct); a text, temporal, binary or UUID column asked for a
  bound; a float column on a dialect that cannot keep NaN out. Or a bound
  table's own filter holds a parameter that has no value. Or the declared
  capabilities cannot hold the plan. Every one of these is raised before
  any query runs, and names the rule that asked. One is raised in running:
  the database refused the statement.
* Fix: bind a declared table and a bind of a known dialect; measure a column
  of a type the adapter knows, and ask for bounds only of a number, a
  decimal or a boolean; give a filter's parameter a value. When the database
  refuses the statement the message names the dataset and the dialect, and
  says when the statement ran in the caller's own transaction, which the
  engine may have left aborted until it is rolled back. Without SQLAlchemy
  installed the adapter names the `sqlalchemy` extra instead.

== dq/compute_support.py

*Content:* 7 `ConfigurationError` sites.

What every compute adapter shares (ADR-010, ADR-014): the order of a plan's
execution, resolving a column by exact name, and converting a bound to an
exact fraction.

* Cause: a portable rule names an `adapter` that does not exist; bindings do
  not exactly match the plan's datasets (a dataset is missing, or a binding
  names one the plan does not require); `execute_envelope` is handed a bare
  plan instead of a `RulesetEnvelope`; a plan names a column that the
  dataset does not have exactly -- and the message lists the columns it
  does have -- or that is ambiguous: a duplicate, or one of two columns
  whose names differ only in case; or a range bound is infinite or of a
  type with no exact fraction.
* Fix: name an adapter the message lists (`spark`, `arrow` or `sql`); align binding
  names with the plan; execute single-semantics plans with `execute_plan`;
  use the column's exact casing; give one of two colliding columns a
  distinct name in the dataset; and keep `Infinity` out of a column a
  ranges/v1 rule measures.

== dq/runner.py

*Content:* 10 `ConfigurationError` sites.

The Spark-free runner and the `dq-run` command (SPEC-015): a rule pack over
files, with the portable engine on the Arrow adapter.

* Cause: the rule pack is not a local file, or its datasets are missing,
  remote, absent or of a format no reader knows. Or what the pack asks for
  cannot be done without Spark: a rule with another engine, a portable rule
  that does not name `adapter = "arrow"`, or a configured sink (a run over
  files does not persist; its evidence is the report). Or the report cannot
  say what it is about: no rule names its dataset and digest, rules on one
  dataset certify two snapshots, `dqframework.dataset` is not a name, or
  several datasets are run and it names none of them. All of these are
  raised before a dataset is read. Two are raised in reading: a file pyarrow
  cannot read, or one with no column in it.
* Fix: give a local rule pack and a `--dataset name=path` for exactly the
  datasets the rules name; keep `adapter = "arrow"` on every portable rule
  and move the others to the `dq-kernel` command; remove
  `dqframework.repository`; give every rule on a dataset one
  `snapshot_sha256`. Without pyarrow installed the runner names the `arrow`
  extra instead.

== dq/run.py

*Content:* 1 `ValidationError` site.

The one run core (ADR-014).

* Cause: a run produced more outcomes, or a larger serialized batch, than it
  is allowed to (`dq.outcomes.MAX_OUTCOMES`, `MAX_BATCH_BYTES`). Evidence
  that cannot be bounded cannot be certified, so the run is refused.
* Fix: split the rule pack, or the dataset, so that one run stays within the
  bounds.

== dq/engine/engine_loader.py

Engine resolution: the name guard, and the manifest of the engine it loads.

* `ValueError` - the engine name is not lowercase alphanumeric with
  optional underscores. Fix the rule's `engine` key.
* `ConfigurationError` - the engine declares an invalid `CAPABILITIES`
  manifest: an unknown capability, a `criticality` that is not `native`,
  `derived` or `absent`, or a flag that is not a boolean. The engine author
  fixes the engine's `CAPABILITIES`. Or the rule names a column by anything
  but a plain identifier where the engine's payload names one (SPEC-025):
  `s.t`, `order id`, `x-y`. Spark reads such a string as an expression, so
  the engine would measure something else. Rename the column upstream, or
  write the check as an expression of your own where the engine takes one.
  The same refusal is a problem `dq-validate` reports.

Outside the counted set, the same place refuses an engine it cannot load with
an `EngineNotFoundError`, and the message says which: a library the engine
needs is not installed -- with the extras that install it, judged before
anything is imported; the engine, or its class, is unknown; or its module
cannot be imported on this machine, with the library's own reason. For the
first, `dq-kernel` exits 2 without starting Spark.

== dq/engine/businessrules/strategies.py

== dq/engine/greatexpectations/greatexpectations_check.py

*Content:* 3 `ConfigurationError` + 3 `ValueError` sites.

Fail-closed expectation resolution and result attribution for the
greatexpectations engine.

* Cause (`ValueError`): an expectation entry has no `type`, or the `type`
  does not resolve to a GX Core expectation class. Or two entries are the
  same expectation to GX -- one type, the same arguments and severity --
  under different names: GX keeps one copy of such a pair and runs it
  once, or runs both and reports two results nothing could tell apart.
* Fix: give every entry a snake-case GX expectation `type` (e.g.
  `expect_column_values_to_not_be_null`), and give two entries of one type
  different arguments, or remove one.
* Cause (`ConfigurationError`): a validation result could not be attributed
  to an expectation. GX returned a result that matches none of the
  configured expectations, a result two expectations match equally, two
  results for one expectation, or none for one. Results are matched to
  expectations by the type, arguments and severity they carry, never by
  position, so this means GX reported something other than the suite's own
  expectations.
* Fix: this is not caused by the data. Check that the `great_expectations`
  version is inside the supported range (`>=1.24,<2`) and that no two
  entries differ only in `meta` or `notes`; then read the positions and
  check names in the message against the rule's `expectations`.


== dq/engine/dqx/dqx_check.py

Fail-closed DQX metadata check construction for the dqx engine.

* `ValueError` -- the rule has no `checks` list, an entry lacks a `check`
  block or `check.function`, `criticality` is not `error`/`warn`, or a
  check name is duplicated. Fix the rule's `checks` payload: every entry
  is a DQX metadata check dict
  (`{check = {function = "is_not_null", arguments = {column = "id"}}}`);
  names must be unique so evidence maps unambiguously to rules.

== dq/engine/dqx/dqx_engine.py

DQX engine wiring: client-mode resolution and DQX-side validation gate.

* `ValueError` -- `client.mode` is neither `stub` nor `workspace`, or
  DQX's structural validator rejects the checks (unknown check function,
  bad argument types). Fix `client.mode` (`stub` for workspace-free
  validation, `workspace` with an optional `client.profile`) and correct
  the flagged check definitions; DQX's error message names the offending
  check.

== dq/engine/checkspec.py

Engine-neutral rule identity and severity normalization: the shared check
seam all engines cross for the axes that are truly common. A fourth axis
crosses it without raising: `column_name_problems` returns what is wrong
with the names a rule gives a column (SPEC-025), and the validator and the
loader refuse by it.

* `ValueError` -- an unknown severity spelling reaches `normalize_criticality`
  (accepted: `error`/`warn`, Deequ's `Error`/`Warning`, and common short
  forms), or explicitly configured check names repeat in
  `require_unique_names`, or a `CheckSpec` is built with a severity outside
  the canonical set. Fix the rule payload's `criticality`/`name` fields;
  derived names are exempt from the uniqueness gate.

  `dqframework.repository` block for that rule or pick a
  persistence-capable engine; refusing is load-bearing so evidence

== dq/utils/config_utils.py

The format-neutral rule-pack loader (SPEC-010).

*Content:* 14 `ConfigurationError` sites.

* Cause: the configuration is empty or not a string, mapping, or tree; an
  unsupported URI scheme; a local file that does not exist or cannot be
  read; a remote source that cannot be fetched; or text that is not valid
  HOCON, YAML or JSON (a YAML or JSON pack must be a mapping). Or a key of
  a JSON or YAML pack, or of a mapping, that cannot be kept whole: not
  text, holding both one of pyhocon's structural characters and a double
  quote, or starting or ending with a double quote.
* Fix: the message names the source and, for a parse error, the line and
  column. A bare path must name an existing file; inline HOCON must contain
  a key separator, braces, or a line break. For a key, write it as text
  without a double quote at an edge: a key with a dot in it needs no
  quotes in JSON or YAML, and is quoted in HOCON.

== dq/harvest/base.py

*Content:* 2 `HarvestError` + 2 `ValueError` sites.

The contract every importer goes through (SPEC-013).

* Cause (`HarvestError`): a source is imported under an empty reference; it
  is larger than 64 MiB; or one of the contract's checks refused it -- a
  record holds a status the importer does not know, the source holds no
  check, two checks share a name, or a batch will not cross the outcome
  gate. Every importer refuses through the one function here, so every
  message names the source, the record and its position.
* Fix: read the message; it says which record of which source is at fault. A
  status the importer does not know means the vendor wrote something this
  version does not read: report it with the vendor's version.
* Cause (`ValueError`): internal to parsing JSON -- `NaN`, `Infinity`, or a
  key that repeats in one object. It is caught here and raised as the
  `HarvestError` above; a caller never sees it.
* Fix: none beyond the `HarvestError` it becomes.

== dq/engine/pandera/pandera_check.py

*Content:* 11 `ConfigurationError` sites, and the `ValueError` of
`dq.engine.checkspec` for a repeated label.

The pandera engine's payload: a schema in pandera's own serialized form,
read fail closed (SPEC-017).

* Cause (`ConfigurationError`): the rule has no `schema`, or what it has is
  not a document; the document's `schema_type` names a backend this engine
  does not read (`dataframe` is pandas, `polars_dataframe` is Polars); it
  declares no column; pandera cannot read it; or it says something that
  would not do what it seems to. pandera ignores a key it does not
  recognise, and the schema then validates anything; and it keeps keys this
  engine cannot report on -- `coerce` (pandera would validate a cast copy),
  `strict`, a check over the whole frame, `unique` over several columns.
  At run time the same error means pandera reported a failure that is no
  outcome of the schema, or two for one check.
* Fix: write `schema` as pandera's `DataFrameSchema.to_json()` writes it for
  the frame's backend, and keep to what the engine reports on: a column's
  `dtype`, `nullable`, `unique`, `required` and its checks. A refusal names
  the place (`$.columns.amount.between_the_lines`). A failure that is no
  outcome of the schema is not caused by the data: it means pandera
  reported something other than the schema's own checks, and the schema is
  where to look.

== dq/engine/pandera/pandera_engine.py

* Cause (`ConfigurationError`): the backend the schema names cannot be

== dq/profile/profile.py

*Content:* 30 `ConfigurationError` sites.

The profile document: what a bounded summary of a dataset may say (SPEC-019).

* Cause (`ConfigurationError`): a document that is not a profile of this

  it; no digest said at all, where `null` says none was read from a file;
  a snapshot digest that is not 64 lowercase hexadecimal digits; a row

  profile's own level, in its dataset or in a column summary; a `source`
  that is neither `arrow` nor `spark`; text that is not strict JSON -- a
  bare `NaN`, `Infinity` or `-Infinity`, where a profile spells an infinite
  bound as text. Or a column summary that
  cannot be: a measure it omits, where every key of a profile is always
  present; a type that is not one of the profile's families; a count that
  is negative, or a boolean; a bound, a length, a precision or a
  not-a-number count on a type that has none; a bound not spelled as the
  type spells it (a decimal as text, a date as `YYYY-MM-DD`, a timestamp
  without an offset); a least value above its greatest; a scale above its
  precision; a key nothing knows. At the profiler, the same error means a
  float bound was a not-a-number: the profilers keep it out of the bounds,
  so one there is a defect.
* Fix: a profile is written by `dq-profile`; take one from there rather
  than by hand, and read the message for the key it names. A digest is 64
  lowercase hexadecimal digits.

== dq/profile/arrow.py

*Content:* 3 `ConfigurationError` sites.

The Arrow profiler.

* Cause (`ConfigurationError`): what was given is not a pyarrow `Table`;
  the table names a column twice, which a profile -- one entry per column,
  read by name -- cannot hold; or Arrow itself cannot count or bound a
  column of that type.
* Fix: pass the table `pyarrow` built -- or the one `dq.runner.read_dataset`
  reads -- under names that are each one column's, and for a column Arrow
  cannot measure, read the message: it names the column and the type.

== dq/profile/spark.py

*Content:* 2 `ConfigurationError` sites.

The Spark profiler.

* Cause (`ConfigurationError`): the frame names a column twice, which a
  profile cannot hold; or the aggregate came back as more than one row,
  which would mean the driver saw data.
* Fix: a frame that names a column twice cannot be profiled: give the
  columns names that are each one's own. More than one row is not caused by
  the data or the frame. It means the frame's `agg(..).collect()` did not
  behave as an aggregate; check the Spark version -- the profiler is
  verified on the 3.5 line.

== dq/profile/suggest.py

*Content:* 4 `ConfigurationError` sites.

The suggesters: a profile in, a draft rule pack out.

* Cause (`ConfigurationError`): a vocabulary that is not one of
  `portable`, `deequ`, `dqx` and `greatexpectations`; a portable rule with
  no snapshot digest to certify; a format that is not HOCON, YAML or JSON;
  or a path whose extension names none of them.
* Fix: name a vocabulary the registry knows, give a portable draft its
  digest (`--snapshot-sha256`, or a profile from `dq-profile`, which writes
  the digest of the bytes it read), and write to `.conf`, `.hocon`,
  `.yaml`, `.yml` or `.json` -- or pass `--format`.

== dq/profile/cli.py

*Content:* 7 `ConfigurationError` sites.

The `dq-profile` and `dq-suggest` commands.

* Cause (`ConfigurationError`): the dataset is not there, or its
  directory holds no file; an approximation of distinct counts was asked of
  Arrow, whose counts are always exact; the Spark profiler was asked to
  read Arrow IPC, or a file whose extension names no format it reads; Spark
  itself could not read the data -- a corrupt Parquet file, whose footer it
  cannot read; a `--format` that contradicts the extension of `--output`;
  or there is no directory to write into.
* Fix: name a dataset that exists; ask `--approximate-distinct` of Spark
  only; give the Spark profiler Parquet, CSV or JSON; let the format follow
  the extension, or name an extension it knows; and write into a directory
  that is there. What Spark said of data it could not read is the message,
  by Spark's error class and without its stack trace (`--verbose` shows the
  trace). Both commands exit 2 for a dataset or a profile they refuse, and
  1 for a failure that is no stated refusal. `dq-suggest` also exits 1 when
  the draft it wrote does not validate -- a defect of the command, not of
  the profile.
