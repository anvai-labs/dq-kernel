= Data Quality Framework reference

This document describes behavior implemented on the current default branch. Documents named
`technical-debt-analysis`, `architecture-improvements`, `performance-optimization`,
`future-enhancements`, and `improvements-index` are planning records, not current guarantees.

== Supported runtime

The tested source matrix is Python 3.12 and 3.13 with PySpark 3.5.9, PyDeequ 1.7.0,
and the Deequ `2.0.21-spark-3.5` JAR. PyDeequ 1.7.0 can map Spark 4.1, but this repository
does not claim Spark 4 or Databricks Runtime 18 compatibility until a separate parity lane
verifies the framework's complete adapter behavior.

The base package can be imported without Spark, PyDeequ, AWS, or Databricks installed. Importing
the `DQFramework` facade and executing built-in distributed engines requires the applicable
extras.

Install the framework path used by the orchestrator and built-in engines:

[source,shell]
----
pip install 'dq-kernel[spark,deequ]'
----

Add `aws` for Glue/S3 support, `databricks` for the Databricks SDK integration, and
`greatexpectations` for the Great Expectations engine. That extra pins GX Core
(`great_expectations >=1.24,<2`) and is imported lazily, so the base package stays GE-free.
Add `sqlalchemy` for the durable SQL sink and `arrow` for its Arrow path; neither is imported
until a SQL sink is configured.

Portable rules also run without Spark at all, over Arrow tables and files: `pip install
'dq-kernel[arrow]'` needs neither Java nor a Spark runtime. See
xref:#running-over-files[Running over files, without Spark].

== Architecture

image::framework-overview.png[Framework components]

The active architecture assessment, debt ledger, and bounded delivery sequence are in
link:modernization-plan.adoc[Architecture Modernization Plan]. The governing incremental
design decision is
link:decisions/adr/ADR-001-incremental-typed-execution-kernel.adoc[ADR-001].
The proposed library-independent rule/metric boundary is
link:decisions/adr/ADR-002-engine-neutral-rule-kernel.adoc[ADR-002].

The implemented execution path is:

. `DQFramework` parses a HOCON string or supported URI.
. `CatalogFactory` selects the Spark, Hive, Unity/Delta, or Glue catalog provider.
. Configured DataFrames are resolved before rule execution; an optional default DataFrame can be
  supplied directly.
. `EngineLoader` resolves the engine through the declarative registry
  (`dq.engine.registry`: one `EngineSpec` per engine), then third-party engines
  registered in the `dq_kernel.engines` entry-point group, then the historical
  `dq.engine.<name>.<name>_engine` naming convention (fallback).
. Each engine returns metric dictionaries. `DQFramework.run()` adds the execution timestamp and
  Spark application ID.
. When a rule supplies repository configuration, supporting engines can append metric and
  verification DataFrames to file paths or catalog tables.

The public base contract is:

[source,python]
----
class DQEngine(ABC):
    @abstractmethod
    def apply(self, dataframe: DataFrame, repository=None) -> list[dict]:
        ...
----

Extension compatibility is explicit:

* `repository` receives the framework's outcome sink (an `OutcomeSink` from
  `dq.sinks`), not raw storage configuration. Engines hand their bounded
  artifacts to the sink; they must not write to files, tables, or catalogs
  themselves.
* Catalog and SQL identifiers must parse through `dq.identifiers`
  (`TableName`, `ColumnName`) so malformed or injected names fail before any
  Spark call.
* The businessrules constraint surface is frozen by ADR-003: its canonical names are
  permanent contracts, and new constraints require kernel-backed semantics
  first.
* Persistence belongs to sinks: engines hand bounded artifacts to the
  injected `OutcomeSink`, durable backends implement `run_scope` so a run is
  one transaction (ADR-006), and drivers are injected by deployment — the
  framework never holds credentials or imports storage drivers.

== Configuration loading

A rule pack may be written in HOCON (`.conf`, `.hocon`), YAML (`.yaml`, `.yml`) or JSON
(`.json`); the format follows the file extension. Every format and every source normalizes to the
same configuration, and `dq-validate` validates all of them without loading an engine.

`DQFramework(spark, config, default_dataframe=None)` accepts:

* an inline HOCON string;
* a path to a rule-pack file, with or without `file://`;
* `s3://` when the AWS extra and credentials are available;
* `abfss://` in a Spark environment configured for ADLS Gen2; or
* `http://` or `https://` (the HTTP helper applies a request timeout).

Unknown URI schemes raise `ConfigurationError`. `dq-validate` fully parses local, `file://` and
inline configuration; remote schemes fail validation. Materialize an immutable local copy first.

Validation proceeds in stages and reports every problem of the first failing stage: the syntax,
the envelope against the published schema, the shape of each rule, then each built-in engine's
required payload (declared in `dq/engine/registry.py`; an extension engine owns its own). The whole
rule pack is validated before any engine runs, so a broken rule never costs the earlier rules'
Spark work.

The rule-pack envelope is described by `dq/schemas/rule-pack.schema.json`, which ships in the wheel
and can be wired into an editor. Engine payloads are intentionally left open there.

[source,shell]
----
dq-validate rules.yaml --format json
----

The JSON output carries `config`, `format`, `valid` and `errors`, so a pre-flight check can be
scripted.

Writing HOCON: pyhocon reads one `key = value` per line inside `{ ... }`. Several keys on one line
is a parse error, and the loader names the line and the file to fix.

Overlays: use one entry file per environment that includes a shared pack and overrides keys.

[source,hocon]
----
include "base.conf"
dqframework.dataset = "orders-prod"
# Unset -> the base value stands; set -> that policy.
dqframework.gate.fail_on = ${?DQ_GATE_FAIL_ON}
----

Variables are not substituted inside `include` paths: `include "env/${ENV}.conf"` silently includes
nothing. Secrets never appear in a rule pack; they arrive through `${?VAR}` or an `url_env`
reference. See `examples/overlays/`.

A minimal Deequ configuration is:

[source,hocon]
----
dqframework {
  dqrules = [
    {
      name = "completeness_checks"
      engine = "deequ"
      dataframes = ["default"]
      checks = [
        {
          constraint_name = "id_complete"
          constraint = "isComplete"
          column = "id"
          level = "Error"
        }
      ]
    }
  ]
}
----

Pass the DataFrame as `default_dataframe`, or declare table-backed frames:

[source,hocon]
----
dqframework {
  catalog_type = "unity"
  dataframes {
    orders = "main.sales.orders"
    customers {
      catalog = "main"
      database = "sales"
      table = "customers"
    }
  }
  dqrules = []
}
----

Table identifiers are limited to one-, two-, or three-part alphanumeric/underscore identifiers;
arbitrary SQL expressions are not accepted as table names.

== Catalog providers

`catalog_type` supports:

* `spark` (default fallback) and `hive`, both through Spark's catalog;
* `unity` and `delta`, through the Unity Catalog provider; and
* `glue`, through the AWS Glue provider.

When `catalog_type` is omitted, the factory checks Spark configuration for Unity/Delta or Glue
markers and otherwise selects `spark`. Catalog permissions and cloud credentials are supplied by
the runtime; the framework does not embed them.

== Engines

Non-Spark compute rides the same plugin contract, and the portable kernel's own semantics
run over Arrow with no Spark session -- pandas, Polars and DataFusion frames included. See
xref:compute-engines.adoc[Compute engines beyond Spark] for the Arrow adapter, the vendor
support matrix and engine recipes.

A rule asks for a column by a name that is a plain identifier: letters, digits and
underscores, starting with a letter or an underscore, at most 128 characters. Spark reads
any other string as an expression -- `s.t` is the field `t` of a struct `s`, and `x-y` is a
subtraction -- and a check would measure something else without a word. So `dq-validate`
and every engine refuse such a name before any data is read, with the reason. Rename the
column upstream, or write the check as an expression of your own where an engine takes one:
a Deequ `assertion`, DQX's `sql_expression`, a DQDL `ruleset`. `dq-profile` profiles a column
whatever it is called, and `dq-suggest` suggests nothing for one no rule can name
(SPEC-025).

=== Deequ

The `deequ` engine maps supported HOCON constraints to PyDeequ checks and requires the matching
Deequ JAR on the Spark classpath. The checked-in local example uses:

[source,python]
----
SparkSession.builder \
    .config("spark.jars", "lib/deequ-2.0.21-spark-3.5.jar") \
    .getOrCreate()
----

[[outcome-contract]]
=== Outcome contract

The facade and evidence reporter use an immutable `CheckOutcome` compatibility
boundary. Summaries require Boolean success and finite, strict JSON diagnostics;
Spark summary Rows export named fields. Exports are independent copies. The
boundary rejects more than 10,000 outcomes, 1 MiB per outcome, 16 MiB per batch/run,
10,000 diagnostic nodes per outcome, or depth 16. It does not truncate evidence
or bound upstream dataset collection. Portable rule planning has landed for
counts/v1 and groups/v1; durable post-validation persistence remains proposed
under ADR-002.

Each result carries three keys:

* `check` -- the check's label. Evidence is attributed by it, so labels are
  unique within a rule: a check is named by its configured name, else by its
  kind and columns (`isComplete_id`), and a rule whose two checks would report
  the same label is refused. Every engine follows this rule; before 0.3.0 the
  Deequ, Great Expectations, businessrules and schema-validation engines
  reported several checks under one name.
* `success` -- that check's own verdict. Where several constraints share one
  Deequ Check (the `single_check_mode` flag, and schema validation's default),
  a passing constraint is reported as passed even when a sibling fails.
* `details` -- engine diagnostics in strict JSON, with `criticality`
  (`error` or `warn`) whenever the engine reports severity.

See xref:writing-an-engine.adoc[Writing an engine] for the engine side of
this contract.

=== Portable count plans

The opt-in `dq.plan` API owns immutable `DatasetRef`, `ColumnRef`, `Predicate`,
`RuleSpec`, `MetricKey`, `CapabilitySet`, and `ExecutionPlan` values. It uses only
the standard library and framework exceptions/outcomes. No engine is imported.
Run `python -m examples.portable_counts` from a source checkout for an executable
fixture demonstration, not a real admission report.

[cols="1,3",options="header"]
|===
|Contract |`counts/v1` meaning
|Input identity |Case-sensitive logical dataset alias plus SHA-256 of a snapshot
whose identity covers both data and schema. The caller/adapter verifies the bytes;
the kernel only validates the supplied identity's shape.
|Columns |One case-sensitive portable identifier, up to 128 ASCII characters.
Nested paths, quoting, expressions and SQL filters are not accepted.
|Row count |Exact global count including rows containing null/NaN; unsigned 64-bit.
|Present count |Exact global count excluding null and floating-point NaN in the
selected column. Empty strings and infinities are present: completeness is not
a finite-value or nonblank check.
|Size |Integer count compared with an integral threshold.
|Completeness |Present/rows, compared as an exact fraction against a finite
Decimal threshold in [0,1]. Empty input fails, even when the threshold is zero.
|Predicates |GE, GT, LE, LT, EQ only; no executable expressions, binary-float
thresholds, approximations, or implicit rounding. Decimal precision and exponent
are bounded to 38 digits and [-38,38].
|Failure |Missing, extra, malformed, snapshot-mismatched or inconsistent metrics
are execution errors, not failed quality measurements. Warning severity never
turns a failed check into passing `dq-report/v1` evidence.
|===

Rules are sorted by unique stable ID. Plans reject empty/mutable rule collections,
more than 10,000 rules, and conflicting snapshot bindings for one alias. A tuple
of deduplicated metric keys includes snapshot, column, kind and semantic version;
plans cannot mix semantic versions.
The canonical JSON SHA-256 is cached; it is independent of rule input order,
Decimal trailing zeros, and adapter identity. Adapter name/version is recorded
separately in outcomes. `dq.spark_adapter` computes all of a dataset's metrics in
one shared aggregate action, so duplicate metric requests cost a single scan.

`validate_for(capabilities)` rejects unsupported metrics or semantic versions.
`evaluate(counts, capabilities)` repeats that check, validates the complete metric
set, and returns immutable outcomes. Counts must describe the complete snapshot:
partition counts may be summed, but partition completeness ratios must not be
averaged without weighting by row count. Only summaries cross this boundary.

Capability declarations are promises, not proof. The built-in `dq.spark_adapter`
advertises `counts/v1` for size and completeness and is verified against
hand-computed fixtures covering nulls, NaN and infinities, decimals, empty
inputs, case-sensitive columns, and repartitioning. A differential suite
(`dq.tests.test_spark_adapter_differential`) runs the same rules through
PyDeequ and the native adapter and pins the one intentional divergence:
counts/v1 excludes floating-point NaN from present counts while Deequ's
completeness counts it, so NaN-bearing columns can pass in PyDeequ and fail
natively past thresholds between the two ratios. On empty inputs both engines
fail completeness. Snapshot digests remain caller-certified.

`dq.portable_config` translates exactly representable HOCON rules --
`isComplete`, `hasCompleteness`, `hasSize`, `DistinctnessByGroup`,
`isNonNegative` and `isInRange` -- and fails closed on everything else: the
check is never approximated and never silently swapped for another engine.
Uniqueness, schema, regex and clocks/timezones remain outside it.

A plan runs on the compute a rule names. `adapter = "spark"`, the default, runs it on
Spark; `adapter = "arrow"` runs it on the Arrow adapter, inside the Spark facade or with no
Spark at all; `adapter = "sql"` runs it where the data already lives, as one aggregate query a
database answers (SPEC-016, DuckDB the certified lane). Any other value is refused before data
is read. Every adapter is held to the same semantic corpus, and
xref:#running-over-files[the runner] executes the same run core as the facade.
xref:compute-engines.adoc[Compute engines beyond Spark] describes the Arrow and SQL adapters.

Outcomes carry the rule ID, exact numerator/denominator, semantic version, logical
plan digest and adapter declaration. `build_report` accepts these outcomes, but
the plan digest does not replace approved rule-set/dataset digests or establish
durable promotion authority. Existing engine entry points are unchanged.

=== DQDL compatibility

PyDeequ 1.7 adds Deequ Data Quality Definition Language support. The `dqdl` engine accepts a
non-empty `ruleset` and returns one bounded outcome per rule. It deliberately does not collect
row-level results into framework outcomes. DQDL is a vendor-specific compatibility adapter, not
the portable rule model proposed by ADR-002. See `examples/dqdl_validation.conf`.

For offline deployment, add both `lib/deequ-2.0.21-spark-3.5.jar` and `lib/dqdl-1.0.0.jar`
to `spark.jars` (comma-separated). The second artifact is `software.amazon.glue:dqdl:1.0.0`,
declared by Deequ's published POM; the Deequ JAR alone cannot execute DQDL. Alternatively,
resolve `pydeequ.deequ_maven_coord` using `spark.jars.packages` before creating the session.
Keep runtime dependencies aligned with the tested Spark distribution.

`max_outcomes` defaults to 1000 and may be set from 1 to 10000. Excess outcomes, zero outcomes,
missing rule identities, or unknown statuses raise errors. DQDL rejects repository persistence
configuration; use `--report-json` for summary evidence. Cross-dataset DQDL rules and row-level
quarantine are not exposed by this adapter yet.

=== Schema validation

The `schemavalidation` engine uses Deequ plus Spark schema inspection for datatype, nullable,
unique, and foreign-key checks. See `examples/schema_validation.conf`.

=== Custom constraints

The `businessrules` engine currently implements `DistinctnessByGroup`, `RateOfChange`,
`LookupBasedOnColumnNameList`, and `WideTablesNegativeValuesCheck`. See
`examples/businessrules_constraints.conf`.

[[great-expectations]]
=== Great Expectations

The `greatexpectations` engine is a first-class engine on GX Core (`great_expectations
>=1.24,<2`), installed with its optional extra (`poetry install -E greatexpectations` in a
source checkout, or `pip install 'dq-kernel[greatexpectations]'`). It validates a Spark
DataFrame through the modern GX datasource API — an ephemeral context, a Spark dataframe
asset, and one `ExpectationSuite` per rule — with the batch definition built once per engine
and reused across runs. Each expectation entry uses a snake-case `type` resolved against
`gx.expectations`; unknown or missing types fail closed with `ValueError`. Result payloads
are sanitized to strict JSON before crossing the outcome boundary, and repository runs
persist metrics and verifications under one millisecond key without requiring PyDeequ. CI
installs the extra and certifies live GX Core round trips (`dq/tests/test_greatexpectations.py`,
skipped only when the extra is absent); mocked-gx unit contract tests run in
`dq/tests/test_greatexpectations_unit.py`. See `examples/greatexpectations_validation.conf`.

[[pandera]]
=== pandera

The `pandera` engine validates a pandas or a Polars DataFrame against a schema in
pandera's own serialized form (`pandera >=0.36,<0.37`, installed with its optional
extra: `poetry install -E pandera` in a source checkout, or
`pip install 'dq-kernel[pandera]'`). The extra brings pandera alone; the frame's
library comes with the frames. It is the first engine whose frame is not a Spark
DataFrame. It is called with a frame in hand, and it declares no persistence: the
framework's artifact path takes a Spark session from the frame. A caller with a
session can still frame its outcomes for a sink, as a harvester's are.

A rule's `schema` is the document `DataFrameSchema.to_json()` writes, so a schema
already in use travels into a rule pack unchanged. The document names its backend:
`schema_type = "dataframe"` is pandas and `"polars_dataframe"` is Polars. A column
admits no null and must be present unless the document says otherwise, and a check
marked `raise_warning = true` is reported with criticality `warn`. The engine is
loaded like any other, and given its frame:

[source,python]
----
import pandas as pd
from pyhocon import ConfigFactory

from dq.engine.engine_loader import EngineLoader

rule = ConfigFactory.from_dict(
    {
        "name": "orders",
        "engine": "pandera",
        "schema": {
            "schema_type": "dataframe",
            "columns": {
                "id": {"dtype": "int64", "unique": True},
                "amount": {
                    "dtype": "float64",
                    "greater_than_or_equal_to": {"min_value": 0},
                },
            },
        },
    }
)
orders = pd.DataFrame({"id": [1, 2, 2], "amount": [3.0, -1.0, 5.0]})
outcomes = EngineLoader().load_engine("pandera", rule, 1).apply(orders)
failed = [outcome["check"] for outcome in outcomes if not outcome["success"]]
----

Every check and every column property the schema enforces gets one outcome, passing
or failing. It is named by the name the document gives the check, else by its kind
and its column (`greater_than_or_equal_to_amount`). An outcome carries pandera's
reason and, where pandera counts them, how many rows failed -- never a failing
value. pandera ignores a key it does not recognise, after which the schema
validates anything; so the engine reads the document, writes the schema back out,
and refuses every key of the input that pandera did not keep, naming where it was
written. It also refuses what it cannot report on: `coerce`, `strict`, a check over
the whole frame, `unique` over several columns. CI installs the extra and runs the
engine on both backends (`dq/tests/test_pandera.py`, skipped only when the extra is
absent); the contracts that need no pandera are in `dq/tests/test_pandera_unit.py`.
See `examples/pandera_validation.conf`.

One thing to know about the dependency itself: where pyspark is installed, importing
pandera sets `PYARROW_IGNORE_TIMEZONE` and `SPARK_LOCAL_IP` for the whole process, as
importing `pyspark.pandas` does, and pyarrow then reads a zoned Python datetime's wall
time as if it were UTC. That is pandera's doing, not the engine's: the engine loads
pandera when a rule first runs, and nothing in `dq-kernel` depends on the switch. A
process that converts zoned timestamps through pyarrow beside this engine should set
the variable itself, to the value it wants.

== Results and repositories

`DQFramework.run()` returns a list of dictionaries containing at least `check`, `success`,
`details`, `ts`, and `jobid` for results emitted by an engine.

Repository configuration is optional. The current helper requires `dataset`, accepts formats
`parquet`, `csv`, `json`, `delta`, or `orc`, and supports:

[source,hocon]
----
repository {
  dataset = "orders"
  format = "delta"
  file {
    paths = ["/quality/results"]
  }
  catalog {
    tables = ["quality.orders"]
  }
}
----

The helper appends partitioned file results and appends to or creates catalog tables with metric
suffixes. It does not implement retries, alert delivery, retention, or access control; those are
deployment responsibilities.

=== Durable SQL sink

`repository { type = "postgres" }` keeps evidence in a SQL database instead of files (ADR-006):
one run is one transaction, a write repeated under the same key adds nothing, and a failed run
leaves nothing behind. The sink is `dq.sqlalchemy_sink.SqlAlchemyOutcomeSink`, built on
SQLAlchemy Core and taking an injected `Engine` or `Connection`; `PostgresOutcomeSink` is the
same class under its earlier name. See `examples/durable_evidence.conf`.

[source,hocon]
----
repository {
  type = "postgres"
  dataset = "orders"
  dsn_env = "DQ_POSTGRES_DSN"
  schema = "dq"
  namespace = "team_a"
  retention_days = 30
  arrow = true
}
----

The environment variable named by `dsn_env` (default `DQ_POSTGRES_DSN`) holds the database
location, which is a SQLAlchemy URL such as `postgresql+psycopg://user@host/quality`. A URL
written `postgresql://` means the psycopg 3 driver, as it always did, and a libpq keyword/value
DSN (`host=... dbname=...`) is read by psycopg 3 too. Credentials stay in the environment and
never appear in a rule pack. The driver is the deployment's to install (`pip install
"psycopg[binary]"`); a missing driver or dialect is reported when the sink is built, before
any rule runs.

PostgreSQL is the certified database, and the only one the sink is tested against a real server
of (`DQ_TEST_POSTGRES_URL=... pytest dq/tests/test_sqlalchemy_sink_postgres.py`). The statements
use forms other databases also accept and the DDL is compiled for the engine's own dialect, but
nothing else is certified. Schema, table and namespace names are validated by `dq.identifiers`
and quoted only where the dialect requires it, so a mixed-case schema keeps its case.

`sink.ddl_statements()` returns the reference DDL for operators, the two evidence tables and the
`runs_completed` and `latest_per_dataset` views; provisioning belongs to deployment and
re-running it is idempotent. `sink.verify_schema()` checks that both tables exist and returns
their row counts. `sink.prune()` deletes artifacts before runs older than the cutoff, within the
sink's namespace unless `all_namespaces=True`, and requires `retention_days`. A `Connection` the
caller owns is never closed by the sink, and inside the caller's transaction a run is a
savepoint.

Each artifact row is stored as one JSON document, made strict first: a NaN becomes `null`, and a
decimal or a timestamp becomes its text, because a `jsonb` column refuses what Python's `json`
module writes for a NaN. A timestamp is stored as wall time without its offset.

With the `arrow` extra installed, a Spark DataFrame's rows are read through Arrow (PySpark 3.5
has no public export, so its `_collect_as_arrow` is used when it is there), and a pyarrow table,
or anything that exports the Arrow stream interface (Polars, pandas, DuckDB, DataFusion), is
read directly. Otherwise the frame's own rows are read. Either way the stored payload is the
same. `arrow = false` turns it off. How a frame is read is known in one place,
`dq.arrow_adapter.table_of`, which every Arrow reader shares.

Install with `pip install dq-kernel[sqlalchemy]`, adding `[arrow]` for the Arrow path.

[[observing-a-run]]
== Observing a run

A run explains itself through one port. `DQFramework.run()` tells an
observer five things, in this order: that it started, that a rule started,
that the rule finished, that the run finished, and what the gate decided.
What an observer does with that is its own affair -- write log lines, open
tracing spans, keep the events -- and none of it can change the run. Every
notification is an immutable record, and an observer that raises is logged
and swallowed, as a notifier is.

[cols="1,3",options="header"]
|===
| Notification | What it carries

| `run_started`
| The run key, the job id, the dataset, and how many rule applications are to
  come.

| `rule_started`
| The run key, the rule's name, the engine, and the dataset.

| `rule_finished`
| The same, and how long the application took in milliseconds, how many
  checks it produced and which of them failed; and, when it raised, the
  error.

| `run_finished`
| The run key, the job id, the dataset, the run's duration, how many rule
  applications it made, how many checks it produced and how many failed, how
  many failures block and how many are advisory; and, when it raised, the
  error.

| `gate_event`
| The `GateEvent` the notifier receives.
|===

A rule event is one application of a rule to one dataset: a rule that names
several datasets gets a pair per dataset. A rule with no name is `rule N`.

A run that goes wrong is still explained. A rule that raises is announced as
finished, with the error and the time it took, and the exception then
propagates as it always did. A run that raises is still announced as
finished, with the error; no gate event follows, because no decision was
reached.

=== The logging observer

With nothing configured, the run is logged: one line per notification, under
the `dq.run_events` logger. Every line names the run, and a line about a rule
names the rule and the engine.

[source]
----
run_started run_key=1700000000000 job_id=local-abc dataset=orders rules=2
rule_started run_key=1700000000000 rule=orders_id_complete engine=deequ dataset=default
rule_finished run_key=1700000000000 rule=orders_id_complete engine=deequ dataset=default duration_ms=842.1 outcomes=3 failed=1
run_finished run_key=1700000000000 job_id=local-abc dataset=orders duration_ms=900.0 rules=2 outcomes=4 failed=1 blocking=1 advisory=0
gate_event run_key=1700000000000 dataset=orders status=failed failed=1/4 blocking=1 advisory=0
----

[source,shell]
----
DQ_LOG_FORMAT=json dq-kernel config.conf
----

With `DQ_LOG_FORMAT=json` each line is one JSON object with the same fields
and an `event` naming the notification, for a log pipeline that parses lines.
The variable is read when the run starts.

`dqframework.observers` is read the way `dqframework.notifiers` is:

* `logging` is the default when nothing is configured. A configured list

=== The OpenTelemetry adapter

With the `otel` extra (`pip install dq-kernel[otel]`), an `otel` observer
opens one span per run and one per rule application, and keeps one counter:

* The spans `dq.run` and `dq.rule` carry `dq.run_key`, `dq.rule`, `dq.engine`
  and `dq.dataset`, and `dq.duration_ms` once they end. The run span also
  carries `dq.gate_passed`, `dq.blocking` and `dq.advisory`. A rule or run
  that raised ends its span in the error status, with the error as its
  description.
* The counter `dq.outcomes` counts outcomes by `dq.status` (`passed` or
  `failed`) and `dq.criticality` (`error` or `warn` for a failed check; `n/a`
  for a passed one, which the gate event does not say).

The extra provides `opentelemetry-api` and nothing else. The application
brings its own SDK, exporter and providers, as OpenTelemetry instrumentation
is meant to compose:

[source,python]
----
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider

trace.set_tracer_provider(TracerProvider())  # and your exporter
----

[IMPORTANT]
Until providers are configured, OpenTelemetry's own proxies accept every
call and record nothing. An `otel` observer with no SDK behind it is silent,
not failing.

[[running-over-files]]
== Running over files, without Spark

The Spark facade needs a session. Most teams outside a lakehouse have none, so the same run
core -- the rule loop, the outcome boundary, the gate policy, the observers and the
notifiers -- also binds to files read with Arrow, and writes the same `dq-report/v1`. Nothing
is written to a sink: the report is the evidence.

Install the path with the `arrow` extra, which brings pyarrow and needs neither Java nor Spark:

[source,shell]
----
pip install 'dq-kernel[arrow]'
----

A portable rule opts in by naming the adapter. The shipped example runs one rule per semantic
version over one file:

[source,hocon]
----
include::../examples/arrow_rule.conf[]
----

Name each dataset the rules use and where it is, and where the report goes:

[source,shell]
----
dq-run examples/arrow_rule.conf --dataset orders=orders.parquet --report report.json
----

`--dataset` takes `NAME=PATH` and is repeated for each dataset. A file is read by its
extension: `.parquet` and `.pq`, `.arrow`, `.feather` and `.ipc`, `.csv`, `.json` and
`.ndjson`; a directory is read as the dataset pyarrow finds in it. Parquet and Arrow IPC keep
every type. A CSV keeps none -- pyarrow decides each column's type, a decimal becomes a double,
and a NaN reads back as null -- and JSON must be newline-delimited. Each dataset is read whole
into memory: a run over files is for data that fits in one process. The command prints a
summary and exits 0 when the gate passed, 1 when it failed, and 2 when the rule pack cannot be
run as given or a dependency is missing.

The same run is a function call:

[source,python]
----
from dq.runner import run

result = run("examples/arrow_rule.conf", {"orders": "orders.parquet"}, report="report.json")
result.decision.passed
----

=== What is refused, and when

The runner does not substitute anything. Each of these is refused before a dataset is read,
and all of them are reported at once:

* a rule whose engine is not `portable`: it needs Spark, and the `dq-kernel` command runs it;
* a portable rule that does not say `adapter = "arrow"`, one that names `spark` included;
* `dqframework.repository`: a sink that is configured and never written would hold no evidence;
* a dataset a rule needs that was not given, one that is given and no rule uses, one that is
  remote, absent, or of an extension no reader knows.

Two refusals come while reading: a file pyarrow cannot read, and one with no column in it.

=== What the report says it is about

The report's dataset is named and digested by what the rule pack says, never worked out from
the files. The name is `dqframework.dataset`, or the one dataset the rules run on; a run over
several datasets must say which one its evidence is about. The digest is the `snapshot_sha256`
the rules certify for that dataset, and the rules on one dataset must agree on it. The report's
`runtime.spark` is null and its `application_id` is `dq-run`.

=== From Python, over any Arrow table

`dq.arrow_adapter` takes a pyarrow table, a record batch, anything that exports Arrow's stream
interface (a Polars, DataFusion or pandas frame), or a Spark DataFrame through its Arrow
export, and imports no library but pyarrow. The frame is bound under the name the plan's
dataset has:

[source,python]
----
import decimal

import polars as pl

from dq.arrow_adapter import execute_plan
from dq.sdk.fixtures import DATASET_NAME, build_plan, load_cases

case = load_cases()[0]  # dataset "ds": columns id, score, amount
plan = build_plan(case)
frame = pl.DataFrame(
    {
        "id": ["a", None, "c", None, "b"],
        "score": [1.5, float("nan"), None, 2.0, 3.0],
        "amount": pl.Series(
            [None, None, decimal.Decimal("3.50"), None, decimal.Decimal("2.00")],
            dtype=pl.Decimal(10, 2),
        ),
    }
)
outcomes = execute_plan(plan, {DATASET_NAME: frame})
[(outcome.to_legacy()["check"], outcome.success) for outcome in outcomes]
----

The frame needs every column its plan's rules name, and names it exactly; the first corpus case
is a counts/v1 plan over `id`, `score` and `amount`.

xref:compute-engines.adoc[Compute engines beyond Spark] lists the routes, what is done to a
column before it is measured, and what is refused.

[[importing-evidence]]
== Importing evidence

Quality results produced by other tools join the same evidence stream: the
same outcome contract, report, gate and sinks as the framework's own. ADR-011
federates rather than competes with platform-native checks -- a signal's
origin is metadata, not a silo.

`dq.harvest` reads three kinds of source. It imports no vendor library to do
it: a harvester parses bytes.

* dbt's `run_results.json`: the data tests, by their `unique_id`;
* a Great Expectations validation result, as `to_json_dict()` writes it;
* a columnar file -- CSV, or a JSON array of records -- with the columns
  `check`, `success`, an optional `criticality` and an optional `details`
  object, so any tool can federate through a trivial format.

[source,python]
----
from pathlib import Path

from dq.gate import evaluate_gate
from dq.harvest import harvest

source = Path("target/run_results.json").read_bytes()
outcomes = harvest(source, reference="target/run_results.json")
decision = evaluate_gate(outcomes, "error")
----

The system is told from the document, or stated with `harvest(source,
reference=..., system="dbt")`. A source is read once: the digest in its
evidence is of exactly the bytes that were parsed.

Each outcome is an ordinary outcome dictionary
(xref:#outcome-contract[Outcome contract]), and
carries where it came from in `details.origin`:

[source,json]
----
{
  "check": "test.analytics.not_null_orders_order_id.cf6c17daed",
  "success": false,
  "details": {
    "criticality": "error",
    "status": "fail",
    "observed": {"failures": 3, "execution_time": 0.1875},
    "origin": {
      "system": "dbt",
      "reference": "target/run_results.json",
      "sha256": "<64 hex digits>",
      "run": "11cfc1e8-98df-4b89-9570-fc85ee756525"
    }
  }
}
----

`status` is the source's own word for the outcome. `observed` holds counts
and measurements, never a row of data. `run` is there when the source names
the run that produced it.

=== What a dbt artifact becomes

Only data tests are imported: records whose `unique_id` begins `test.`. A
model, seed or snapshot is not a quality result, and a unit test judges a
model's logic on fixed inputs. The `unique_id` is the label.

[cols="1,1,1,3",options="header"]
|===
| dbt status | `success` | `criticality` | Why

| `pass`
| true
| error
| Evaluated. Neither threshold was met.

| `fail`
| false
| error
| Evaluated. The `error_if` threshold was met.

| `warn`
| false
| warn
| Evaluated. Only the `warn_if` threshold was met.

| `error`
| false
| error
| The test's own query failed. Nothing was judged.

| `skipped`
| false
| error
| `dbt build` skips every test that follows a failed one. Nothing was judged.
|===

The artifact does not record a test's configured severity, so a test that
was not evaluated cannot be read as advisory: no verdict is not a pass.

=== What a Great Expectations result becomes

One outcome per expectation result, labelled as the
xref:#great-expectations[greatexpectations engine] labels the same
expectation: its type and column, `expect_column_values_to_not_be_null_id`.
A `severity` of `warning` makes the check advisory.

`observed` keeps the numbers at the top level of a result: `unexpected_count`,
`element_count`, an `observed_value` where it is a number. Lists, strings and
nested objects are not copied, which leaves out `partial_unexpected_list`
and `partial_unexpected_counts` (row values), `partial_unexpected_index_list`
(row locators) and the traceback a raised expectation carries. A raised
expectation comes back as `success: false` with an empty `result`, and is a
failed check.

=== The columnar format

One record per check:

[source,csv]
----
include::../examples/import/checks.csv[]
----

`check` is the label and must be unique in the file. `success` is required:
a JSON boolean, or a CSV cell reading `true` or `false`. `criticality` takes
the spellings every engine takes and is `error` when absent. `details` is an
object (in CSV, that object as JSON in one cell) and becomes `observed`. Any
other column is refused, so that nothing is dropped without a word. What a
tool writes in `details` is the tool's to judge: this format cannot recognise
a row of data.

=== A source that cannot be imported

A record either normalizes into the outcome contract or the source is
rejected. Importing never widens the contract. The refusal is a
`HarvestError`, which is a `ConfigurationError`, and its message names the
record and its position:

[source]
----
columnar source 'checks.csv': row 4: 'orders_id_unique' has success 'yes', which is not true or false
dbt source 'target/run_results.json': record 7: 'test.proj.x' has status 'skip', which is not a dbt data-test status
----

A source is also refused when it holds no check at all -- an empty Great
Expectations suite validates with `success: true`, and the artifact of a
`dbt run` holds models and no tests -- when two checks share a name, when it
is not UTF-8, or when it is over 64 MiB. Only the fields a harvester reads
are required; others are ignored, since dbt writes fields its own published
schema does not list.

=== Sending imported outcomes to a sink

Frame them as the framework frames its own, with
`dq.engine.dq_engine.outcome_frames(spark, outcomes)`. Do not hand the
outcome dictionaries to `spark.createDataFrame` and let it infer a schema:
their `details` differ in shape from one check to the next, and Spark then
infers a map of strings and writes every nested value as its `str()` -- no
error, the structure gone. `outcome_frames` states the schema.

=== dq-import

[source,shell]
----
dq-import target/run_results.json --dataset-id orders \
    --dataset-sha256 <64 hex digits> --report-json evidence.json
dq-import examples/import/checks.csv --fail-on error
----

`dq-import` reads a source once, applies the gate policy, and writes a
`dq-report/v1` document in which `rule_set` names the imported document with
the digest of the bytes that were parsed. `runtime.spark` is `null`.
`--report-json` needs `--dataset-id` and `--dataset-sha256`, as it does for
`dq-kernel`; without a report the command still applies the gate and prints
its verdict. It exits 0 when the gate passed, 1 when it failed, and 2 when
the source was rejected.

The checked-in examples under `examples/import/` are imported by the tests.

[[profiling-and-suggestion]]
=== dq-profile and dq-suggest

Start from the data instead of a blank rule pack: profile it, then turn the
profile into a draft.

[source,shell]
----
dq-profile --dataset orders=orders.parquet --profile orders.profile.json
dq-suggest orders.profile.json --engine deequ --output orders.deequ.conf
dq-suggest orders.profile.json --engine portable --output orders.portable.yaml
dq-run orders.portable.yaml --dataset orders=orders.parquet --report report.json
----

`dq-profile` summarizes a dataset -- with Arrow by default, or with Spark
(`--profiler spark`) -- and writes the summary as JSON: one bounded entry per
column, saying its type, how many values are null and how many are distinct,
its least and greatest value where the type has an order, and its length
bounds where it has a length. Its size depends on the column count alone.
The two profilers mean the same thing by every number: a null is a SQL null; a
float that is not a number is a value, counted on its own and never a bound; a
signed zero is one value; a timestamp with a zone is spelled in UTC. No column
fails a profile: a nested one, or one of a type the profile does not know, is
typed and counted for nulls.

With Spark the work grows with the column count: 1,000 columns are profiled in
seconds, where one aggregate holding 1,000 exact counts does not finish. For a
table too wide or too cardinal for an exact count, `--approximate-distinct`
has Spark count approximately, and every count in the profile then says
`distinct_exact: false`. The shape of a profile is published as
`dq/schemas/profile.schema.json`, which ships in the wheel; what a shape
cannot say is enforced where a profile is read.

`dq-suggest` turns a profile into a draft rule pack, in HOCON, YAML or JSON,
written in words its engine already accepts -- `portable`, `deequ`, `dqx` or
`greatexpectations`. It suggests three things, each only where the profile
warrants it: that a column with no nulls is complete; that a column exactly
distinct by an exact count is unique (not for the portable subset, which has
no uniqueness check); and that a numeric column whose least value is 0 or
more is non-negative. Every suggested rule is a warning, and the pack names
the gate policy under which a failed warning is reported and blocks nothing
(`gate.fail_on = "error"`): a draft never stops a pipeline. To promote a
rule, raise its criticality; in a rule pack of your own, the gate policy is
yours to set. The command validates what it wrote, and says so when a
profile warrants no rule at all.

A column is profiled whatever it is called, but a suggestion is made only
for one a rule can ask for by name: a name that is a plain identifier. And
a suggestion is made only where the engine's own check would confirm it on
the same data. Two cases are measured. The portable `isComplete` counts a
float that is not a number as missing, where the profile counts it a
value, so the portable draft says nothing of the completeness of such a
column. Deequ's `isComplete` refuses a nested column, so its draft says
nothing of that either. The command names both kinds of column.

A portable rule names the snapshot it certifies, and the framework never
computes a dataset's digest. `dq-profile` read the bytes, so it writes their
SHA-256 into the profile and the portable draft carries it -- which is why
the last line above runs. A profile taken through the Python API has none;
give it one with `--snapshot-sha256`.

The same two steps from Python:

[source,python]
----
import pyarrow as pa

from dq.profile import arrow, suggest

orders = pa.table({"id": [1, 2, 3], "amount": [1.5, None, -3.25]})
profile = arrow.profile_table(orders, "orders")
checks = suggest.suggest(profile, "deequ")["dqframework"]["dqrules"][0]["checks"]
suggested = [(check["constraint"], check["column"]) for check in checks]
----

The amount column has a null and a value below zero, so nothing is suggested
for it; the id column is complete, exactly distinct and never below zero. The
Spark profiler is `dq.profile.spark.profile_frame`, for a DataFrame.

An engine's draft is on the dataset of its profile, by name
(`dataframes = ["orders"]`), and the framework looks for that frame where it
looks for any named dataset: a temp view or table called `orders`, or
`dqframework.dataframes`. A frame passed as `default_dataframe` is not found
under that name. So the Deequ draft written above is loaded like any other
rule pack, once the frame is registered:

[source,python]
----
from dq.dq_framework import DQFramework

orders = spark.read.parquet("orders.parquet")
orders.createOrReplaceTempView("orders")
results = DQFramework(spark, "orders.deequ.conf").run()
failed = [result["check"] for result in results if not result["success"]]
----

Over the data the profile was drawn from nothing fails, so `failed` is
empty. Over a later snapshot a rule may fail: the run reports it, and goes
on.

== Command-line tools

[source,shell]
----
dq-kernel file:///absolute/path/config.conf --spark-master 'local[*]'
dq-validate file:///absolute/path/config.conf --format json
dq-engines --format json
dq-import examples/import/run_results.json --dataset-id orders \
    --dataset-sha256 <64 hex digits> --report-json evidence.json
dq-run examples/arrow_rule.conf --dataset orders=orders.parquet --report report.json
dq-profile --dataset orders=orders.parquet --profile orders.profile.json
dq-suggest orders.profile.json --engine deequ --output orders.deequ.conf
----

`dq-kernel` creates a Spark session, runs the configured checks, prints a summary, and exits
with 0 when the quality gate passed, 1 when it failed (or the run errored), or 2 when the
configuration is invalid or a dependency is missing. `dq-validate` validates required local
configuration structure without running Spark checks. Built-in engines use engine-specific
payloads: Deequ/businessrules use `checks`, schema validation uses `schema`, Great Expectations
uses `expectations`, DQDL uses `ruleset`, DQX uses `checks`, and the portable engine uses `plan`.
Every checked-in example is validated in CI.

`dq-engines` lists the engines this installation can resolve, built-in and
entry-point, with each engine's capability manifest and, for an engine whose
optional dependency is missing, how to install it. `dq-import` reads another
tool's results as evidence and needs no Spark session: see
xref:#importing-evidence[Importing evidence]. `dq-run` runs a rule pack over files with
Arrow and needs no Spark session either: see
xref:#running-over-files[Running over files, without Spark]. `dq-profile` summarizes a dataset
and `dq-suggest` turns the summary into a draft rule pack of warnings: see
xref:#profiling-and-suggestion[dq-profile and dq-suggest]. `DQ_LOG_FORMAT=json` makes a run
log JSON lines: see xref:#observing-a-run[Observing a run].

=== Gate policy

Since every engine reports a canonical `criticality`, you decide which failed checks stop a
pipeline (ADR-013):

[source,hocon]
----
dqframework {
  gate { fail_on = "error" }   // "any" (default) | "error" | "never"
  notifiers = [
    { type = "logging" }
    { type = "webhook", url_env = "DQ_GATE_URL" }
    { type = "slack",  url_env = "SLACK_WEBHOOK_URL" }
    { type = "teams",  url_env = "TEAMS_WEBHOOK_URL" }
  ]
}
----

With the default `any`, behaviour is unchanged: any failed check fails the gate. With `error`, a
check whose `criticality` is `warn` is reported but does not block. The report's `status` never
follows the policy: it states whether any check failed. `summary.blocked` and `summary.warned`
carry the split.

One gate event is announced per run after the run scope has committed (ADR-008). HTTP notifiers
make three attempts with capped exponential backoff and are fail-open: a delivery failure is
logged and never alters the run. Notification is at-most-once; consumers that need more read the
durable evidence store.

== Security boundaries

* Do not place cloud credentials, Databricks tokens, or storage secrets in HOCON files.
* Use runtime-native identity, secret managers, and least-privilege catalog/storage grants.
* Only HTTPS should be used for remote configuration in production.
* Table names are validated, but configuration content remains trusted operational input.
* Databricks automation should use OAuth machine-to-machine or workload identity federation.

See link:databricks-authentication.adoc[Databricks authentication and runtime compatibility].

=== Lakeflow pipeline expectations

`dq.engine.databricks.pipeline_expectations.PipelineExpectationsHarvester`
reads the expectation metrics a Lakeflow Declarative Pipeline already
records (per-dataset pass/drop counts in `flow_progress` events of the
Unity Catalog event log, read from the configured Unity Catalog event-log table (resolved from the pipeline's spec, or a
published table passed directly) or, for managed event logs, the
`event_log('<pipeline_id>')` function) and normalizes
them into the framework outcome contract -- so platform-native checks
join the same report, sinks, and gate as every engine (ADR-011). The
harvester only reads; it never runs validations, and `FAIL UPDATE`
expectations that halt an update emit no aggregate metrics for it to
harvest.

=== Delta Change Data Feed validation

`dq.cdf_adapter` (ADR-011 role B) validates the increment: read a
Delta table's change data feed window (`read_changes`) and evaluate
aggregate checks scoped to the change batch (`execute_cdf_plan`)
through the portable kernel's versioned semantics -- counts,
within-batch distinct bounds, and value ranges over `insert` /
`update_postimage` rows, stamped with the `spark-cdf` adapter. V1 is
change-batch scoped: counts measure change volume (a record committed
twice in the window counts twice), and uniqueness and totals are
evaluated within the change batch only; deduplicated-by-key and
full-table semantics remain future modes. Reading requires the table
property `delta.enableChangeDataFeed=true`; outside Databricks/EMR
install the `delta` extra for the Delta data source.

== Tests and CI

CI runs the Spark-backed test suite on Python 3.12 and 3.13 with Java 17. It rejects missing tests,
enforces 90% combined coverage, independent 90% line and 88% branch floors, and 90% changed-code
coverage, and refuses a coverage report that holds a path outside the checkout. It runs Black,
Flake8, Bandit, and pip-audit, builds the package, and proves the wheel needs no extra: it
installs the wheel alone into an empty environment, where every module of the package must
import except the few declared to need an extra, every command must answer its help, and
anything asked to work without its extra must name it -- a command by exiting with the code
its help promises. It reviews dependency changes, and checks documentation links -- trying
again while only a remote's own failures remain, and asking for a GitHub file page as the
file itself, since those pages answer 503 to everybody for half an hour at a time.

The coverage floors are a ratchet, kept a few points under what CI measures, so that a real drop
fails the build. They stood at 55, 57 and 46 from the first release while coverage rose past 93,
where they could not fail.

The fail-closed aggregate job, `build`, is the check `main`'s branch protection requires:
changes reach `main` by pull request only, and a red `build` stops the merge. Every compute
adapter is held to the same semantic corpus, and the Arrow adapter is measured against the
Spark adapter on real Spark.

The owner path runs only after immutable owner/repository checks and environment approval on
self-hosted capacity. Other pull requests stay on GitHub-hosted runners.
