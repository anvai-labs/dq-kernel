= Compute engines beyond Spark
:toc:
:sectlinks.

Status: current as of 0.3.0 +
Scope: how to run dq-kernel validation over non-Spark compute (pandas,
Polars, Arrow/DataFusion, DuckDB/SQLAlchemy) using the engine plugin
contract (ADR-012), and what each vendor library actually supports.

== Why the plugin contract is compute-agnostic

The engine contract (`dq.engine.dq_engine.DQEngine`) never imports
pyspark: the `dataframe` argument to `apply`/`_prepare`/`_execute` is
the engine-native frame object, duck-typed at the boundary. A non-Spark
engine subclasses `DQEngine`, implements the `_prepare`/`_execute`
hooks, declares its capabilities, and is loaded by the same registry --
with pyspark absent from the environment. The only Spark-coupled default
is the standard persistence path (`_artifact_frames`); engines that
persist differently override `_persist_outcomes` (the same hook deequ
and businessrules already use to keep their native artifact schemas).

PySpark, Ibis, pyarrow and geopandas beside pandas and Polars. The
`pandera` engine reads a schema's document for pandas or for Polars and no
others (SPEC-017); see "pandera" in the user guide.

== The Arrow adapter

The portable kernel's plans run over an Arrow table with no Spark at all:
`dq.arrow_adapter` computes a plan's metrics and hands them to the kernel's
own evaluation (`dq.plan`), so a decision is made in one place whichever
engine computed. A rule opts in by naming the adapter:

[source,hocon]
----
{ name = "orders_complete"
  engine = "portable"
  dataframes = ["orders"]
  dataset = "orders"
  snapshot_sha256 = "<64 hex digits>"
  adapter = "arrow"
  plan = [ { constraint = "isComplete", constraint_name = "id_complete", column = "id", level = "Error" } ] }
----

`adapter` is `spark` when absent. Any other value is refused before data is
read.

The adapter computes what the Spark adapter computes. The same semantic
corpus runs through both, and on real Spark the two agree on every metric,
every decision and every refusal. Where Arrow differs from Spark by
construction, the adapter does the work: Arrow counts `0.0` and `-0.0` as
two distinct values where Spark counts one, so a signed zero is made one
value before anything is counted.

Its surface is the Spark adapter's -- `capabilities_for`, `execute_plan`,
`execute_envelope` and `compute_plan_values` -- and what the two share
lives once, in `dq.compute_support`: which metric kinds each semantic
version defines, the exact-column and exact-fraction refusals, the order a
plan's datasets and groupings are visited, and the plan's execution
itself. A new compute adapter is three callables around that
(`dq.compute_support.ComputeAdapter`) and one entry in
`dq.compute_support.ADAPTER_MODULES`; the SQL adapter is the second built
that way.

=== What a dataset can be

Read, in this order, each found by name on the object, so that no library
but pyarrow is imported (`dq.arrow_adapter.table_of`):

* a pyarrow table, as it is;
* a record batch, or a reader of record batches;
* a Spark DataFrame, through the export it has: `toArrow()` on Spark Connect
  and PySpark 4, the private `_collect_as_arrow()` on classic PySpark 3.5.
  An empty frame exports no batch, so its table is built from the frame's
  column names with no row in it;
* an object with `__arrow_c_stream__`, Arrow's stream interface: Polars,
  DataFusion, pandas 2.2 and later. A Polars `LazyFrame` offers nothing and
  must be collected first;
* an object with `to_arrow_table()`: DataFusion;
* a pandas DataFrame, through pyarrow's own conversion. A pandas index that
  is not the plain range index becomes a column, as pyarrow makes it.

A binding that is none of these is refused by its type.

=== What is done to a column before it is measured

"It is an Arrow column" is not yet "Arrow can compute on it", and the gaps
differ by type and by pyarrow version. Before a column is measured it is
brought to the form every kernel is written for, each step lossless:

* a dictionary-encoded column -- which `pq.read_table` returns for a column
  stored that way -- is decoded. Its type says `dictionary`, not `double`:
  undecoded, a present count cannot tell that a NaN is in it;
* a `string_view` column -- how Polars hands over its strings -- becomes
  `string`;
* a half- or single-precision float is widened to double, and `0.0` is
  added, which makes a signed zero one value;
* `decimal32` and `decimal64` are widened to `decimal128`;
* a null-typed column is given a type: Arrow counts an all-null column of
  the null type as one distinct value, and Spark counts none.

A list, a struct or a map is neither countable distinct nor a bound. Arrow
has no kernel for it, and the adapter refuses with a `ConfigurationError`
that names the dataset, the column and the metric. Nothing is approximated.

== The SQL adapter

The same plans run where the data already lives: `dq.sql_adapter` compiles a
plan into one aggregate `SELECT` per dataset, has the database run it, and
hands the one row it gets back to the kernel's own evaluation. The data does
not move. A rule opts in with `adapter = "sql"`.

A dataset is bound as a `SqlDataset`: a SQLAlchemy table whose columns
declare their types, and the `Engine` or `Connection` that reaches it:

[source,python]
----
from decimal import Decimal

from sqlalchemy import Column, MetaData, Numeric, String, Table, create_engine, text

from dq.plan import (
    ColumnRef,
    Comparison,
    DatasetRef,
    ExecutionPlan,
    Predicate,
    RuleKind,
    RuleSpec,
)
from dq.sql_adapter import SqlDataset, compile_plan, execute_plan

# A dataset: a table whose columns declare their types, and a bind.
orders = Table("orders", MetaData(), Column("id", String), Column("amount", Numeric(10, 2)))
engine = create_engine("duckdb:///:memory:")
orders.create(engine)
with engine.begin() as connection:
    connection.execute(text("INSERT INTO orders VALUES ('a', 1.25), (NULL, 3.50)"))

plan = ExecutionPlan(
    (
        RuleSpec(
            "id_complete",
            DatasetRef("orders", "a" * 64),  # the snapshot the rule was certified for
            RuleKind.COMPLETENESS,
            Predicate(Comparison.EQ, Decimal(1)),
            ColumnRef("id"),
        ),
    )
)
dataset = {"orders": SqlDataset(orders, engine)}

compile_plan(plan, dataset)["orders"]  # the statement, before anything is run
(outcome,) = execute_plan(plan, dataset)
----

The columns are declared, not looked up from the database. Their types decide
the statement -- a float column must have NaN kept out of its present count
and its bounds -- and nothing type-agnostic can find a NaN in DuckDB. The
declared type is what the adapter may assume about the values; it need not be
how the database stores them.

=== What is refused, and when

Everything that can be checked is checked when the bindings are validated,
and nothing reaches the database until that is done. What cannot be honoured
is refused before any query runs, naming the rule that asked for it. The
order matters because a failed statement cannot be taken back: DuckDB has no
savepoint, and it leaves the transaction the statement ran in aborted.

* a column that is not there, exactly named, as every adapter refuses it;
* a dialect the adapter does not know: it knows DuckDB and PostgreSQL, and
  asks nothing of any other;
* a column of a type it cannot measure -- JSON, an array, a struct -- whose
  values may be NaN, or how they compare, is not known;
* a bound of a text, temporal, binary or UUID column: the kernel's bounds are
  numbers, decimals and booleans;
* a float column on a dialect that has no way to keep NaN out;
* a filter of a bound subquery that holds a parameter with no value. Its
  value would be written into the statement as `NULL`, and the query would
  quietly answer about nothing.

=== Two things DuckDB does that the adapter undoes

* *A decimal read through a typed expression comes back rounded.* The DuckDB
  dialect declares that the driver has no native decimal, so SQLAlchemy turns
  what the driver gave -- an exact `Decimal` -- into a `Decimal` again by way
  of a float. A decimal that differs from `0.1` in the twentieth place comes
  back as `0.1`. The adapter runs its statement as text, so the driver's own
  value comes back.
* *A decimal bound as a parameter arrives rounded.* Loaded with a parameter,
  the same decimal is already a double when it reaches the table, even when
  the SQL casts the parameter to the column's type. Bind it as text and cast
  it, or write it as a literal.

And one thing PostgreSQL does not have: no `min` or `max` of a boolean. Where
that is so the bounds are taken of the boolean cast to an integer -- the same
two values, 0 and 1.

DuckDB is the certified lane: its semantics are checked to be the kernel's,
on the corpus and against the Spark adapter on the same rows. The statement
is rendered by the bind's own dialect, or by another one to compile for: every
corpus statement is held as a PostgreSQL snapshot, and was run once by hand
on a real PostgreSQL 14, which is how the boolean came to light.

A bind is built from a URL the environment holds, never from a rule pack. The
table is declared with its columns; it is never reflected (reflection through
duckdb-engine fails on every version combination tried):

[source,python]
----
from sqlalchemy import Column, MetaData, String, Table

from dq.sql_adapter import SqlDataset, engine_from_env

engine = engine_from_env("ORDERS_DATABASE_URL")
orders = Table("orders", MetaData(), Column("id", String))
dataset = {"orders": SqlDataset(orders, engine)}
----

`dq-run` reads files. A SQL rule is run by handing the portable engine a
`SqlDataset` where a Spark rule gets a frame, or by calling the adapter as
above.

== The Spark-free runner

`dq.runner` binds the one run core (`dq.run`) to files read with pyarrow:
the gate policy, the observers and the notifiers of the rule pack all
apply, with no Spark session and no sink. Its evidence is a `dq-report/v1`
document.

[source,shell]
----
pip install 'dq-kernel[arrow]'
dq-run examples/arrow_rule.conf --dataset orders=orders.parquet --report report.json
----

[source,python]
----
from dq.runner import run

result = run("rules.conf", {"orders": "orders.parquet"}, report="report.json")
result.decision.passed
----

A file is read by its extension: `.parquet` and `.pq`, `.arrow`, `.feather`
and `.ipc`, `.csv`, `.json` and `.ndjson`; a directory as the dataset
pyarrow finds in it. Parquet and Arrow IPC keep every type. A CSV keeps
none: pyarrow decides each column's type, a decimal becomes a double, and a
NaN reads back as null. JSON must be newline-delimited, and its types are
told the same way.

The runner does not substitute, and refuses before it reads a dataset:
a rule with another engine, a portable rule that does not name
`adapter = "arrow"` (one naming `spark` included), a configured sink, and a
dataset that is missing, unused, remote, absent or of a format no reader
knows. The operator reference (xref:index.adoc[Data Quality Framework reference],
"Running over files, without Spark") has the details.

== Recipe: a non-Spark engine on the plugin contract

The Arrow adapter is the supported way to run the kernel's semantics
without Spark. An engine of another vocabulary -- one that evaluates its
own predicates over a frame -- still follows the same skeleton: subclass
`DQEngine`, declare `CAPABILITIES` honestly, and implement the two hooks.
A minimal one, drop-in under `dq/engine/<name>/` or an external
distribution registering the `dq_kernel.engines` entry-point group:

[source,python]
----
from dq.engine.checkspec import build_result
from dq.engine.dq_engine import DQEngine


class PandasEngine(DQEngine):
    """Validate a pandas DataFrame; no Spark in the environment."""

    CAPABILITIES = {
        "criticality": "derived",   # kernel synthesizes severity
        "row_filter": True,         # pandas .loc predicates
        "failed_rows": True,        # cheap to count locally
        "persistence": False,       # evidence goes to dq-report/v1 only
    }

    def _prepare(self, dataframe):
        # once-per-engine plumbing: resolve the check payload to
        # (name, predicate) pairs; fail closed on unknown predicates
        return [
            (c["name"], c["predicate"]) for c in self._config.get("checks", [])
        ]

    def _execute(self, dataframe, prepared):
        metrics = []
        for name, predicate in prepared:
            failed = int((~dataframe.eval(predicate)).sum())
            metrics.append(
                build_result(
                    name,
                    failed == 0,
                    {"failed_rows": failed},
                    criticality=self._criticality_for(name),
                )
            )
        return metrics
----

Registry entry (built-in) or entry point (external):

[source,python]
----
EngineSpec("pandas", "dq.engine.pandas.pandas_engine", "PandasEngine", "checks")
----

[source,yaml]
----
# external distribution's packaging metadata
[options.entry_points]
dq_kernel.engines =
    pandas = dq.engine.pandas.pandas_engine:PandasEngine
----

Everything else -- loading, the log preamble, capability-guarded
persistence, `dq-report/v1` evidence, gate events with the severity
split -- comes from the contract.

== Recipe: SQLAlchemy / DuckDB through GX

GX Core evaluates expectations against any SQLAlchemy engine. Inside a
custom engine's `_prepare`, build the ephemeral SQL datasource instead
of the Spark one:

[source,python]
----
def _prepare(self, dataframe):
    import great_expectations as gx  # or dq.utils.imports.require_extra

    context = gx.get_context()
    source = context.data_sources.add_sql(
        name="dq_kernel_sql",
        connection_string="duckdb:///warehouse.duckdb",  # any SQLAlchemy URL
    )
    self._batch_definition = (
        source.add_table_asset(name="orders", table_name="orders")
        .add_batch_definition_whole_table("whole")
    )
    return self._suite()  # GreatexpectationsCheck(...).build_suite(gx, rule)
----

[source,python]
----
def _execute(self, dataframe, prepared):
    batch = self._batch_definition.get_batch()
    validation = batch.validate(prepared)
    return self._extract_metrics(validation)  # build_result + sanitizer
----

Postgres/SQLite/DuckDB/Snowflake all resolve through the SQLAlchemy
URL; the duckdb-engine dialect package provides the DuckDB driver.

== pandas and Polars with the portable semantics

For the kernel's own semantics, a pandas or a Polars frame needs no engine
of its own: it is handed to the Arrow adapter as it is. The frame needs
every column its plan's rules name, and names it exactly:

[source,python]
----
from decimal import Decimal

import polars as pl

from dq.arrow_adapter import execute_plan
from dq.plan import (
    ColumnRef,
    Comparison,
    DatasetRef,
    ExecutionPlan,
    Predicate,
    RuleKind,
    RuleSpec,
)

dataset = DatasetRef("orders", "a" * 64)  # the snapshot the rule was certified for
plan = ExecutionPlan(
    (
        RuleSpec(
            "id_complete",
            dataset,
            RuleKind.COMPLETENESS,
            Predicate(Comparison.EQ, Decimal(1)),
            ColumnRef("id"),
        ),
    )
)
frame = pl.DataFrame({"region": ["east", "east", "west"], "id": ["a", None, "a"]})
(outcome,) = execute_plan(plan, {"orders": frame})
----

The outcome is the kernel's, whichever adapter computed it:
`outcome.to_legacy()["details"]["adapter"]` says `{"name": "arrow", "version": "1"}`.

The operator reference (xref:index.adoc[], "Portable count plans") describes
the rules and the vocabulary.

== What deliberately does not exist

* No universal check vocabulary across engines (ADR-012 keeps vendor
  vocabularies native; only identity/severity cross the seam).
* No automatic translation of vendor rules into portable plans
  (ADR-002); the fail-closed translator accepts the documented subset.
* No persistence from a Spark-free run. The built-in sinks read a Spark
  DataFrame -- `RepositorySink` through its own rows, the SQL sink through
  its Arrow export -- so a run over files writes its evidence as a report
  and refuses a configured sink rather than leave it unwritten.
* No reflection of a table's columns in the SQL adapter. It binds declared
  columns, and table reflection through duckdb-engine fails on every version
  combination tried; a runner that resolves SQL datasets out of a rule pack
  would be new work.
* No warehouse certified but DuckDB. The SQL adapter's statements are
  rendered by each dialect and were run once by hand on PostgreSQL 14; a lane
  of its own is what would certify another database.
