== Purpose

Make a green CI run mean what it says: every lane passed, and any failure
says why. On 2026-11-24 none of that held. `main` had been red for six days
because a dependency-floor commit never regenerated the lock file; the merge
gate ignored a red lane; stacked pull requests ran no CI at all; and no
failing test or collection error printed a traceback.

== In scope

* Lock discipline: `poetry check --lock` in the lint lane, so a
  `pyproject.toml` change without a lock regeneration cannot merge.
* An honest merge gate: the `build` job lists every other lane in `needs`
  and its verify step is generic over that list, so adding a lane cannot
  produce a red job that merges anyway.
* CI on every pull request regardless of its base branch, so stacked pull
  requests are tested.
* Failure visibility: pytest options never silence the summary; subprocess
  contract tests force a collection error and a failing test and assert the
  traceback is printed.
* An explicit lane matrix: the main test lane installs every extra that has
  tests. Extras are co-installable because the lock resolves one version per
  package for the union; an extra with a Python marker is skipped by Poetry
  where it does not apply.
* A unit lane hermetic to which extras are installed.
* Workflow hygiene: actionlint (version-pinned, sha256-verified download)
  and commit-SHA-pinned actions, both enforced by test.
* Repairs: the stale lock on `main`, and the two stacked pull requests.

== Out of scope

* The owner-private workflow and its runner configuration;
* release signing (SPEC-003);
* branch-protection settings — "require `build`" is an owner setting, not
  code, and is recommended rather than specified;
* test-suite performance work.

== Contracts

* `build.needs` equals the set of all other jobs in `ci.yml`.
* The gate passes when every lane is `success` or `skipped`, and on pull
  requests additionally requires `dependency-review` to be `success`.
* The gate runs under `always()`, so a failed lane produces a red gate
  instead of a skipped one.
* The main test lane performs exactly one `poetry install`, naming every
  extra under test.
* The gate script is executed by the workflow contract test against sample
  `needs` maps; it is never checked by pattern matching alone.

== Acceptance gates

* G1 — `main` is green and its lock satisfies `poetry check --lock`.
* G2 — A collection error and a failing test each print their traceback
  under the repository's default pytest options.
* G3 — The gate script, executed against success, failure, cancelled and
  skipped lane results, passes and fails as specified; `build.needs` lists
  every other lane.
* G4 — CI runs on a pull request whose base is not `main`.
* G5 — The main lane installs the `dqx` extra and the live DQX tests run
  and pass in CI on the 3.12 job.
* G6 — The unit lane passes with DQX installed and with it absent.
* G7 — Workflow syntax is linted in CI, and every action is pinned to a
  commit SHA.
* G8 — Pull requests #54 and #55 are green.
