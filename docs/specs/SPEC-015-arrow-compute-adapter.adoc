= SPEC-015: Arrow compute adapter and Spark-free runner
:toc:
:sectlinks.

Status: In Progress — every gate is met in code and by its tests; CI on the carrying PR is awaited +
Date: 2026-11-24 +
Driven by: ADR-010, ADR-002, ADR-014 +
Milestone: M3 +
Depends on: SPEC-011, SPEC-012 +

== Purpose

Evaluate portable plans without a Spark cluster. ADR-010 gated its
Arrow-native engine on "differential equivalence over the shared fixtures";
this spec builds it. Arrow is the interchange standard, so one adapter
reaches pandas, Polars, and DataFusion, which is also the only way most
teams outside a lakehouse will ever run this framework.

== In scope

* `dq.arrow_adapter`: executes counts/v1, groups/v1, and ranges/v1 plans
  over Arrow tables and hands the values to the kernel's own evaluation, so
  decisions are made in exactly one place.
* Input normalization through Arrow interchange: a pyarrow table, a record
  batch, or any object that exports one, is accepted. pandas, Polars, and
  DataFusion are supported through that path and are not dependencies of
  the package (Polars and DataFusion are development dependencies, so the
  tests of that path run in CI).
* A capability set for the adapter. Semantics it cannot honour are declared
  absent so a plan fails closed at validation, never approximates.
* Wiring: `engine = "portable"` with `adapter = "arrow"`, in the Spark
  facade and in the Spark-free runner alike. The adapter is chosen by a
  mapping the SQL adapter (SPEC-016) extends by one entry.
* A shared run core (`dq/run.py`) that owns the rule loop, outcome
  normalization, the gate policy, notifiers, and observers — extracted from
  `DQFramework.run()` so that a second runner reuses it rather than copying
  it.
* A Spark-free runner (`dq.runner`) and a `dq-run` command: datasets read
  with pyarrow.dataset (Parquet, CSV, JSON), the gate policy applied, and
  `dq-report/v1` written.

== Out of scope

* Arrow-native rebuilds of vendor engines (Deequ, Great Expectations, DQX);
* distributed Arrow runtimes;
* streaming;
* a query planner: the adapter computes the kernel's metrics and nothing
  more.

== Contracts

* The adapter produces the same metric values the Spark adapter does for
  every fixture the kernel defines, including null, NaN, decimal, and
  empty-input cases.
* Only bounded summaries leave the compute layer: one aggregate row per
  dataset.
* `dq.arrow_adapter` imports with pyarrow absent (it fails closed when used
  without it) and with every other extra blocked.
* The Arrow adapter's surface is the Spark adapter's: a name and version, a
  capability set per semantic version, `capabilities_for`, `execute_plan`,
  `execute_envelope`, and `compute_plan_values`. Both convert a bound to an
  exact fraction and resolve a column by exact name through one shared
  function each, with the same messages, so a case that fails closed does so
  identically on either adapter.
* `DQFramework` remains the Spark facade (ADR-001); its behaviour and its
  return type do not change.

== Acceptance gates

* G1 — The Arrow adapter passes the shared fixture corpus in full, including
  the null, NaN, decimal, and empty-input cases.
* G2 — A direct Spark-versus-Arrow differential over the same data agrees on
  every plan in the corpus.
* G3 — pandas, Polars, and DataFusion frames are accepted through Arrow
  interchange (each tested when its library is installed).
* G4 — `dq-run` completes an end-to-end run and writes a valid
  `dq-report/v1` in a process where importing Spark fails.
* G5 — `dq.arrow_adapter`, `dq.runner`, and `dq.run` import with all extras
  blocked.
* G6 — The Spark facade's outcomes are unchanged by extracting the run core
  (the existing framework contract tests pass unmodified).

[NOTE]
====
Amended 2026-11-26, before implementation, and again after it. The facts
below were read from the code and from probing pyarrow 16.0.0, 24.0.0 and
26.0.1, polars 2.2.0, datafusion 55.0.0 and Spark 3.5.9. Two sentences of
the first amendment were wrong; they are corrected below rather than left
to be read.

* The adapter honours all three semantic versions, so its capability sets
  declare the same metric kinds as the Spark adapter's. "Declared absent so
  a plan fails closed" is the kernel's own `validate_for`; a test shows a
  plan that needs a kind the adapter does not declare being refused.
* What "exports an Arrow table" means, in order: a pyarrow table; a record
  batch, or a reader of them; a Spark DataFrame, through `toArrow()` (Spark
  Connect, PySpark 4) or `_collect_as_arrow()`, which is private in PySpark
  3.5 and returns no batch for an empty frame -- an empty frame gives a
  table with the frame's column names and no rows; an object with
  `__arrow_c_stream__` (Polars, DataFusion, pandas 2.2 and later); one with
  `to_arrow_table()` (DataFusion); and a pandas DataFrame through pyarrow's
  own conversion. This is the one place that knows how to get an Arrow
  table out of a Spark frame; the SQL sink's (SPEC-007) calls it.
  Corrected: the first amendment also named `__arrow_c_dataframe__`. No
  library offers it and pyarrow consumes none; it was written from memory.
* An Arrow column is not yet a column Arrow can compute on, and the gaps
  differ by type and by version. Half-float has no `equal`, `add` or
  `min_max` kernel on any version from 16 to 26; `decimal32` and
  `decimal64` have no `min_max`; a null-typed column has no `count_distinct`
  and reports one distinct value where Spark reports none; `string_view`,
  which is how Polars hands over its strings, has no `min_max`,
  `count_distinct` or `filter` kernel, and no grouping on pyarrow 24. So a
  column is brought to the form every kernel is written for before it is
  measured, each step lossless: narrow floats are widened to double, narrow
  decimals to `decimal128`, a view becomes a string, a null-typed column is
  given a type.
* Dictionary-encoded columns are decoded first. Corrected: the first
  amendment said an adapter that skipped this would pass every corpus case.
  It would not. An encoded column's type says `dictionary`, not `double`, so
  a present count that has not decoded it cannot tell that a NaN is in it,
  and counts the NaN as present -- with no error; nor has it a bound.
  `pq.read_table` returns a column that way when the file stored it so. The
  corpus is therefore also run with every column encoded.
* Signed zero. Arrow counts `0.0` and `-0.0` as two distinct values and
  groups them apart; Spark counts them as one (`countDistinct` over
  `[0.0, -0.0, 1.0, 1.0, 2.0, 2.0]` is 3 in Spark and 4 in Arrow). The
  adapter adds `0.0` to every float column, as a double: IEEE arithmetic
  turns `-0.0` into `0.0` by that and leaves every other value alone. It has
  to be done that way, because half-float has no `equal` kernel to find the
  zeros by; and it is done to grouping keys as well as to measured columns.
  The corpus gained five cases, each verified on a real Spark session before
  it was written: the two signed-zero ones, an empty ranges input, a `-0.0`
  bound that is zero, and boolean bounds.
* NaN is absent for a present count and for a range's count and bounds, and
  is one distinct value in a group -- in Arrow as in Spark, verified on both.
* Bounds come back from Arrow as the Python types Spark gives: `int`, `float`,
  `Decimal`, `bool`, `date`, `str`. A `date` is refused with the same
  "unsupported type" the Spark adapter gives.
* An error of Arrow's own during a computation becomes a `ConfigurationError`
  naming the dataset, the column and the metric, so the adapter fails closed
  instead of surfacing, say, an `ArrowNotImplementedError`. A list or a
  struct is neither countable distinct nor a bound, and is refused that way.
  For a groups plan the keys are grouped and each measured column counted in
  a step of its own, because Arrow counts distinct values in a hash table
  and reports a list it cannot count as a key it cannot group on.
* `adapter` on a portable rule is `spark` when absent, or `arrow`. Any other
  value is refused before data is read. The key itself is not checked by
  `dq-validate`, which has no rules for the portable payload, and payloads
  stay open (SPEC-010) -- so a misspelled key means the default. The value
  being checked is what this spec adds.
* The run core, `dq.run.run_rules`, takes the rules, two things a runner
  supplies -- load an engine for a rule at the run key, and resolve a dataset
  name to a frame -- and the run's collaborators: sink, observer, a notifier
  to build, the gate policy, the job id, the dataset name and the clock. It
  returns the outcomes, the gate decision and the gate event. The Spark
  facade keeps its signature and return type, and what is its own: loading
  configuration, catalogs, and the Spark application id. The plan's
  execution itself -- validate against the adapter's capabilities, check the
  bindings, compute, evaluate -- lives once in `dq.compute_support`, with
  what the Spark, Arrow and SQL adapters share.
* `dq-run` names its datasets on the command line, `--dataset name=path`,
  with the format from the file's extension: Parquet, Arrow IPC, CSV and
  newline-delimited JSON; a directory is read as the dataset pyarrow finds
  in it. Parquet and IPC keep every type; a CSV keeps none (a decimal becomes
  a double, a NaN reads back as null), and JSON's types are told. It refuses,
  before reading any dataset and all at once, a rule whose engine needs
  Spark, a portable rule that does not say `adapter = "arrow"` (it refuses
  rather than substitute an adapter), a configured sink (its evidence is the
  report), and a dataset that is missing, unused, remote, absent or of a
  format no reader knows. Two refusals come in reading: a file pyarrow
  cannot read, and one with no column in it -- pyarrow reads a directory
  holding nothing it recognises as no file and no column, and says nothing.
  Its report has `runtime.spark` null and the job id `dq-run`, and names the
  dataset it is about by what the rule pack says: `dqframework.dataset`, or
  the one dataset the rules run on, digested by the `snapshot_sha256` the
  rules certify, which must agree. The digest is never worked out from the
  files.
* For G3, `polars` and `datafusion` become development dependencies so the
  interchange tests run in CI rather than skip: a test that always skips
  verifies nothing. pyarrow itself imports pandas when pandas is installed,
  so "nothing but pyarrow is imported" is tested by making the libraries
  absent, not by forbidding their import. datafusion requires pyarrow, so
  a development install now holds pyarrow without the `arrow` extra; which
  modules need none of it is therefore shown by blocking it, as G5 does.
* For G2, the differential is two-fold: every corpus case on both adapters
  over the same data, and a randomized differential over generated tables
  with signed zeros, NaN, nulls and decimals in them, so an edge the corpus
  lacks is still caught. The generated rules put every threshold on a
  boundary the data makes, and the table is measured a third way, by a
  reference in plain Python, so the two adapters cannot agree on a shared
  mistake. Two deliberate mutations were used to see it fail.
* `examples/portable_rule.conf`, the Spark example, had gone stale -- a size
  check written as `min = 1`, which the translator refuses -- and nothing
  ran it. It is repaired, and a test now runs each example.
