= SPEC-011: Engine SDK and conformance kit
:toc:
:sectlinks.

Date: 2026-11-24 +
Driven by: ADR-012, ADR-002 +

== Purpose

Make third-party engines first-class. ADR-012 defined the engine contract
but left it implicit in the built-in engines and in internal tests. This
spec turns that contract into something an engine author outside this
repository can run, and gives every compute adapter one shared fixture
corpus.

== In scope

* `dq.sdk.conformance`: `assert_engine_conforms(...)` and a pytest-friendly
  suite factory that any engine's own tests can call. It checks that
  capabilities are valid; the template order holds (guard, log, prepare,
  execute, persist); results pass the strict outcome gate; criticality is
  canonical; persistence honours the declared capability; artifacts land
  under the injected run key; and two runs over the same input give the same
  outcomes.
* One differential fixture corpus under `dq/sdk/fixtures/`, with expected
  outcomes per semantic version, and a loader for it. The Spark adapter's
  differential tests consume it now; the Arrow and SQL adapters will
  (SPEC-015, SPEC-016).
* `scripts/new_engine.py NAME`: scaffolds an engine module with the hooks
  and capabilities, its unit tests with fakes, and an example rule pack, and
  prints the registry line to add.
* `dq-engines`: lists registry and entry-point engines with capabilities and
  payload key, and reports which extras are installed, with install hints.
* Property-based tests (Hypothesis, a development dependency) for the pure
  kernel functions: the sanitizer, outcome normalization, and fingerprint
  canonicalization.
* Documentation: a "Writing an engine" guide.

== Out of scope

* A plugin registry service or marketplace;
* loading a Python path from configuration (ADR-001 non-goal);
* certifying an engine's *semantics* — the kit certifies contract
  conformance; semantic equivalence is the differential fixtures' job.

== Contracts

* `dq.sdk` imports with every optional dependency blocked and never imports
  a vendor library itself.
* The conformance API takes callables (an engine factory and a frame
  factory); it imports no engine module.
* A violation is reported with the check that failed and the offending
  value.

== Acceptance gates

* G1 — Every built-in engine passes the conformance suite (engines whose
  extra is absent skip).
* G2 — A deliberately non-conforming engine — wrong result shape, missing
  criticality, ignoring its declared persistence capability — is rejected
  with a message naming the violated check.
* G3 — The Spark adapter's differential tests run on the shared corpus and
  pass in full.
* G4 — The scaffold's output passes lint, its own unit tests, and the
  registry drift guard without manual edits.
* G5 — `dq-engines` lists built-in and entry-point engines with
  capabilities; its JSON output is covered by a snapshot test.
* G6 — The property tests run in the unit lane.

====
Amended 2026-11-24, during implementation.

* The suite, run against the built-in engines for the first time, found two
  evidence defects that no existing test covered, and fixing them became part
  of this spec because G1 cannot be true without it. Four engines (Deequ,
  Great Expectations, businessrules, schema validation) reported several
  checks under one name, so evidence could not be attributed to a rule. And
  wherever several constraints shared one Deequ Check, a passing constraint
  was reported as failed as soon as a sibling failed. The labelling rule now
  lives in the check seam (`labels_for_checks`, `require_unique_labels`), and
  a constraint's verdict is its own.
* "The registry drift guard" in G4 is read as all the guards a new engine
  must satisfy: the drift guard, the registry snapshot, the error catalog,
  and example validation. The scaffold updates each.
* A capability manifest is now inherited from the parent class. Merging over
  the base defaults instead silently reset whatever a parent had declared,
  which the suite's own deliberately broken engines exposed.
* The corpus carries its expectations in two layers -- the metrics an adapter
  must compute, and the decisions that follow from them through the kernel.
  The pure check caught a wrong expectation in the first draft (a size
  rule) that no adapter had yet been run against, and a probe corrected a
  claim about Deequ on empty input that had been written from memory.
* One configuration is pinned as a known upstream defect rather than made to
  pass: schema validation in multi-check mode with both not-null and unique
  constraints crashes inside pydeequ, with the old Check names as well as the
  new ones.
* The scaffold test measured itself into the parent's coverage report.
  pytest-cov arms every child process, so the pytest runs inside the scratch
  copies were merged into the report as two more `dq` trees -- 148 files that
  are not in this repository, all untested. With pytest-cov 6 that took line
  coverage from 92.8% to 37%; with the locked pytest-cov 7 it did not happen
  at all, so CI would have stayed green while a developer's local run failed
  the floor. The children are no longer armed (`test_scaffold.py`), and the
  coverage gate now refuses a report that holds a path outside the checkout
  instead of averaging it in (`dq/tests/test_coverage_gate.py`).
* The corpus validator accepted cells no engine can store as written, and
  Spark does not refuse them either: a decimal `NaN` is stored as null, and
  `1.234` in a `decimal(10,2)` column as `1.23`. A case carrying such a cell
  would pass validation and run on data other than the one it documents. A
  cell must now fit its column exactly (finite, within scale and precision,
  within 64 bits for a long), and a cell the validator cannot judge is
  reported rather than raised on.
* Three ways an engine can fail were reported by the conformance suite but
  had no test: failing on its second run, failing when handed a repository,
  and failing on the keyed run. They have one each
  (`test_conformance_unit.py`), as do the Deequ matcher's refusals
  (`test_deequ_attribution_unit.py`).
