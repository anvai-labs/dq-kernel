= SPEC-012: Gate policy and notifier conformance

:sectlinks.

== Purpose

Give severity operational meaning, and bring the notifier up to the decision
its ADR records. Since ADR-012 every engine reports a canonical
`criticality`, yet a warn-only failure still exits the pipeline with code 1
and marks the report failed. The webhook notifier makes one attempt where
ADR-008 specifies three, the gate event is emitted inside the run scope
where ADR-008 requires it after the scope commits, and nothing can inject a
recording notifier into a run.

== In scope

* `dq.gate`: `GatePolicy` (`any`, `error`, `never`), `GateDecision`, and
  the pure function `evaluate_gate(outcomes, policy)`. Configuration key:
  `dqframework.gate.fail_on`.
* Exit codes for `dq-kernel`: 0 when the gate passes, 1 when it fails, 2
  when the run fails because the configuration is invalid or an optional
  dependency is missing. Today every failure returns 1, so a caller cannot
  tell a data problem from a typo.
* `dq-report/v1`: additive `summary.blocked` and `summary.warned` counts.
  `status` keeps its meaning: any failed check.
* Notifier conformance with ADR-008 and SPEC-002: the `notifiers` key (it
  supersedes `notify`), three webhook attempts with capped exponential
  backoff and an injectable sleep, a `report` reference on `GateEvent`, an
  `InMemoryNotifier`, `slack` and `teams` adapters, the event emitted after
  the run scope commits, and constructor injection of a notifier.

== Out of scope

* Per-rule or per-check routing;
* a message templating language;
* e-mail and SMS adapters;
* delivery guarantees beyond at-most-once.

== Contracts

* The default policy is `any`, which preserves today's exit behaviour
  exactly. `error` makes warn-only failures non-gating. `never` reports but
  never fails.
* `evaluate_gate` is pure and is the one place the decision is made; the
  CLI reads from it.
* An outcome with no `criticality` counts as `error`.
* `dq-report/v1` and the gate event gain keys only.
* A notifier that raises is logged and swallowed by the framework, whatever
  the adapter does.

== Acceptance gates

* G1 — For every policy and outcome mix (error failure, warn failure, both,
  none) the decision and the exit code are as specified.
* G2 — Under the default policy the CLI exit codes are identical to before
  for rule packs without warn failures, and the report is identical apart
  from the two additive summary keys.
* G3 — The webhook adapter makes three attempts with backoff on transport
  failure and then gives up without raising; a success on a later attempt
  stops the retries; tests inject the sleep and touch no network.
* G4 — A recording notifier receives exactly one event per run, for passing
  and failing runs, carrying the report reference when one is configured;
  the event is emitted after the run scope has exited.
* G5 — The Slack and Teams adapters post their shaped payloads and are
  fail-open.
* G6 — The report with the additive summary fields still validates; the
  existing report tests pass with only their exact-equality assertion on
  `summary` extended for the two new keys.

[NOTE]
====
Amended 2026-11-24, before implementation started and after reading the
code. The original text listed a fourth policy, `warn`, which would have
been an alias for `any` (a warn failure and an error failure both block),
so it is removed. The original G2 required the report bytes to be identical
to before, which contradicted the additive summary keys; it now requires
identity apart from those keys. The original G6 said the existing report
tests would be unchanged; one of them asserts exact equality on `summary`
and has to be extended. The original scope did not mention that the gate
event is emitted inside the run scope today, which ADR-008 forbids.
The HTTP adapters also accept only `http` and `https` URLs: the URL arrives
through the environment, and without the allow-list a mis-set variable could
point an adapter at a local file.
