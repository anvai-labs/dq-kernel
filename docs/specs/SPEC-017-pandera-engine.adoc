== Purpose

Wrap pandera, the most widely used schema and dataframe validation library
in the pandas and Polars ecosystem, so its users get this framework's
evidence and gate without rewriting their checks. It is the first engine
whose input is not a Spark DataFrame.

== In scope

* `dq/engine/pandera/`: an engine on the ADR-012 hooks that validates a
  pandas or a Polars DataFrame.
* Payload in pandera's own vocabulary. A rule's `schema` is the document
  pandera's `to_json()` writes: a nested mapping in HOCON, YAML or JSON, or
  that document as a text. The document names its backend:
  `schema_type = "dataframe"` is pandas and `"polars_dataframe"` is Polars.
  No Python is loaded from configuration (ADR-001 non-goal), so a reference
  to a schema object or a function in a module is out.
* Results: one outcome per check and per column property the schema
  enforces, passing and failing alike. Each carries pandera's reason and,
  where pandera counts them, how many rows failed -- never a failing value.
* Severity: a check pandera is told to treat as a warning (`raise_warning`)
  is reported with `criticality: warn`; every other outcome is an `error`.
* An optional `pandera` extra, and live tests in the main test lane.

== Out of scope

* Custom check functions written in Python and referenced from a rule pack.
  A serialized schema cannot carry one; see the note.
* Schema inference (that is profiling, SPEC-019).
* Backends beyond pandas and Polars.
* Persistence to a repository. The framework's artifact path builds Spark
  frames from the frame's own session, and a pandas or Polars frame has
  none, so the engine declares `persistence` false and refuses one.
* A runner that resolves a frame for a schema out of a rule pack. The
  engine is called with a frame in hand (`dq-run` reads files for portable
  rules, SPEC-015).

== Contracts

* Capabilities are declared honestly: no row filter; failed-row counts
  where pandera gives them; no persistence.
* Vendor vocabulary passes through untouched. Only identity and severity
  cross the check seam.
* The engine imports no pandera until it is used.
* Nothing pandera drops silently gets through. pandera ignores a check or a
  key it does not recognise, and the schema then validates anything. So the
  engine reads the document, writes the schema back out, and refuses every
  key of the input that is missing from pandera's own document at the same
  place. What pandera keeps but the engine cannot report on is refused by
  name.
* A result is matched to its check by what the failure carries -- the
  column and the check's name -- never by its position.
* A warning-level check is never reported as passed on pandera's word
  alone: under lazy validation pandera says nothing about one that fails.

== Acceptance gates

* G1 — The live dependency and API check is recorded here: versions
  installed, the calls verified against the real package, and the date.
* G2 — The engine passes the conformance suite (SPEC-011) on a pandas frame
  and on a Polars frame, with attribution checked against a schema whose
  columns are in another order.
* G3 — Live round trips on each backend. A passing schema, a failing column
  check, a wrong dtype, a null in a non-nullable column, a duplicate where
  `unique` is declared, a missing required column and a failing
  warning-level check each produce the specified outcomes.
* G4 — An unknown construct or a document pandera cannot read fails closed
  with a message naming the check.
* G5 — A checked-in example rule pack validates and is covered by a test.

Amended 2026-11-27, before any build, with what the gate check measured: an
isolated environment on Python 3.13 with pandera 0.36.0 (released
2026-11-10), pandas 3.1.1 and Polars 2.2.0. Three of the spec's first
sentences did not survive it and are rewritten above rather than left to be
read.

* The dependency is safe to add. With `pandera = "^0.36"` as an optional
  dependency and one `pandera` extra, the lock gains three packages
  (pandera 0.36.0, typeguard 4.6.1 and typing-inspect 0.9.0) and moves no
  version. Poetry cannot name a dependency's own extras, so the extra is
  pandera alone: `pandera[pandas]` would add only numpy and pandas, and
  `pandera[polars]` only polars. The frame's library comes with the frames.
* The classes are imported per backend. `from pandera import Check` warns
  that the top-level names will be removed; the engine uses `pandera.pandas`
  and `pandera.polars`.
* A schema is written with `to_json()` and read with
  `DataFrameSchema.from_json()`. The document is keyed: a column holds at
  most one check of each kind (`greater_than_or_equal_to`, `str_length`,
  `isin`, ...), with its statistics and optionally `error` and
  `raise_warning`. A `checks` list on a column is not a document pandera
  reads: it raises a bare `KeyError: 'options'`, which the engine turns into
  a refusal. So a column and a check's name identify a check.
* A check's argument is written bare when the statistic is all there is, on
  both backends, and as a mapping when the check says more. The two spell
  the statistic differently: pandas keys it `min_value` and `max_value`,
  Polars `value`. The comparison the Contracts ask for equates a one-key
  mapping with the bare value, or correct documents would be refused.
  (*Corrected after the build:* the first amendment gave the bare form to
  Polars alone.)
* *Corrected:* G3 asked for a failing dataframe-level check. One written as
  a Python function cannot be serialized -- pandera warns that only
  registered checks may be serialized and writes `"checks": null` -- and
  ADR-001 forbids loading the function from configuration. G3 names the
  column properties a document does carry instead.
* Under lazy validation pandera reports nothing for a warning-level check
  that fails. It is absent from `SchemaErrors.schema_errors`, and when only
  such checks fail, `validate()` returns the frame. The engine makes every
  such check strict in the schema it keeps before it validates, and
  remembers which they were.
* A failure carries `column_name`, `reason_code`, `check` and
  `failure_cases`. `check` is a `Check` for a column check, and a bare name
  for a column property: `not_nullable`, `field_uniqueness`, the dtype. On
  pandas it is the schema's own object; on Polars a copy. So a result is
  matched on the column and the check's name.
* `failure_cases` is a DataFrame for a check, a null, a duplicate and a
  dtype the column's values do not fit. Its length is the number of failed
  rows, and it holds the failing values themselves -- which is why an
  outcome carries a count and never a value. Elsewhere it is a string: the
  column's name when a required column is absent (then `column_name` is
  `None` and the reason `COLUMN_NOT_IN_DATAFRAME`), or the dtype a whole
  column has when it is the wrong one. The engine reports a count only
  where pandera gave one.
* One cause can be two failures. On pandas a null in an integer column
  turns the column to float, and pandera reports both the null and the
  dtype. The engine reports both.
* A required column that is absent fails every outcome of that column, with
  that reason and no count. An optional column that is absent raises
  nothing: its outcomes pass, with `present: false` in their details.
* pandas 3 stores text as `str`, so `"dtype": "object"` fails a text column
  there. The example writes `str`.
* Persistence is out. `DQEngine._artifact_frames` takes the session from the
  frame, and a pandas or Polars frame has none. A caller with a session can
  still frame the outcomes for a sink, as a harvester's are
  (`dq.engine.dq_engine.outcome_frames`).

Amended again on the same date, after the build, with what building it
measured. Each is held by a test in `dq/tests/test_pandera.py` or
`test_pandera_unit.py`.

* A column admits no null and must be present unless the document says
  otherwise: pandera's defaults are `nullable = false` and `required = true`.
  So a column with no check still has outcomes -- its dtype and its nulls --
  and an absent optional column is the one that says `required = false`.
* A check may carry a `name`. A `Check` keeps the document's key as its
  `registry_name` and the author's name as its `name`, on both backends, and
  a failure carries the author's name. A check is reported under the name
  the document gives it, else under its kind and its column, as every engine
  names a check. Two outcomes that would share a name are refused.
* What pandera keeps and the engine refuses by name, and why:

** `coerce` -- pandera validates a cast copy of the column, so the outcome
   would vouch for data the frame does not hold;
** `strict` -- an extra column fails as `column_in_schema`, with no column
   to carry it;
** a schema-level `checks` list, and `unique` over several columns -- they
   fail with no column too.

  The first version of the engine reports on a column's checks and its
  dtype, nullability and uniqueness. Any other key pandera keeps is refused
  the same way, as not something this engine reports on.
* A backend whose library is not installed is refused in its own words. The
  first build asked for the backend inside the `try` that wraps pandera's
  parser errors, so "could not read the document" came first, which was not
  what went wrong; a mutation of that line is what showed no test could
  tell the two apart.
* A whole column of the wrong dtype is counted on pandas (the values that
  do not fit) and only named on Polars (the dtype it has). Either way no
  failing value reaches evidence.
* Something that is not a frame is raised as it came. pandera's own error
  is not a validation failure, and the engine reports nothing about it.
* Importing pandera is not without effect on the process. Where pyspark is
  installed, its import sets `PYARROW_IGNORE_TIMEZONE` and `SPARK_LOCAL_IP`
  in the environment, as importing `pyspark.pandas` does; and pyarrow reads
  the first on every conversion of a Python sequence, any value at all,
  reading a zoned value's wall time as if it were UTC. Nothing in
  `dq-kernel` depends on the switch, and its tests are written so that it
  moves nothing. The full suite showed why that matters: one existing test
  built an Arrow column from a zoned value, and failed as soon as the
  pandera tests had been collected. It says its instant in UTC now, and
  `test_pandera.py` holds the fact itself.
* pandera 0.36.0 ships more backends than pandas and Polars: of those in the
  lock, PySpark, Ibis, pyarrow and geopandas. The engine reads a document
  for `dataframe` and for `polars_dataframe` and nothing else.
