Driven by: ADR-012, ADR-011 +
Milestone: M3 +

== Purpose

Wrap Soda Core so that SodaCL checks — the checks many data teams already
have — run over their warehouse and land in the same evidence stream as
everything else.

== In scope

* `dq/engine/soda/`: an engine on the ADR-012 hooks.
* Payload: a SodaCL check set as a YAML mapping. Data source and connection
  come from the engine configuration, with credentials from the environment.
* Results: one outcome per check with its outcome, the measured value where
  Soda reports one, and a bounded diagnostic.
* An optional `soda` extra and live tests against DuckDB in the main test
  lane. *This is the line the gate stopped:* as an extra, Soda Core moves
  two packages for every install. Whether it ships another way is the
  owner's decision (see the note).

== Out of scope

* Soda Cloud (any hosted product);
* Soda's own alerting and scheduling;
* programmatic checks written in Python.

== Contracts

* Capabilities are declared honestly; Soda's `warn` outcome maps to the
  `warn` criticality.
* The engine imports no Soda package until it is used.
* A skipped check is reported as skipped, never as passed.

== Acceptance gates

* G1 — The live dependency and API check is recorded here: versions
  installed, the calls verified against the real package, the date, and the
  result of co-installing with the other extras.
* G2 — The engine passes the conformance suite (SPEC-011).
* G3 — Live round trips against DuckDB: passing, failing, warning, and
  skipped checks each produce the specified outcomes.
* G4 — An invalid SodaCL document fails closed with Soda's message preserved
  as the cause.
* G5 — A checked-in example rule pack validates and is covered by a test.

[NOTE]
====
Amended 2026-11-28. The Gate said what to do if Soda Core could not coexist
with the other extras: become Blocked with the conflict recorded, and not
force it. That is what happened, and this is the record.

* **What was measured.** soda-core's newest release is 4.32.0 (2026-11-25;
  the spec first recorded 4.31.0), Python >=3.10. Of its eight requirements,
  two are caps: `ruamel.yaml<0.19,>=0.18.17` and `requests<2.34.0,>=2.32.3`.
  The lock holds ruamel-yaml 0.19.1 and requests 2.34.2. Read from PyPI's
  own metadata on 2026-11-27 and again on 2026-11-28.
* **Why it is everyone's downgrade.** Poetry resolves one version of a
  package for the union of all extras. So a `soda` extra would not stay
  inside itself: in the trial lock of 2026-11-27, `requests` went
  2.34.2 → 2.33.1 and `ruamel-yaml` 0.19.1 → 0.18.17 for every install,
  whatever extras it asked for. It also brought twelve packages, among them
  an OpenTelemetry exporter and sqlglot.
* **The caps may lift.** Soda Core releases about weekly (4.30.0 on
  2026-11-05, 4.31.0 on 2026-11-17, 4.32.0 on 2026-11-25). Re-read
  `requires_dist` on PyPI before this spec is unblocked.
* **Not measured, and not to be read as such:** the API half of the gate.
  No Soda package was installed and no call of it was verified.

*The owner's decision, on 2026-11-27:* to go on to M4 and to mark this spec
truthfully meanwhile. What remains theirs is how, or whether, to ship it:

. **Install alongside, with no extra and nothing in the lock** (the
   recommendation). The engine would load Soda where it finds it. Its live
   tests would run only where Soda is installed, so no CI lane would certify
   it unless one installed Soda outside the lock, and the shipped wheel
   would say only that the engine is there.
. **Accept the two downgrades for every install.** They are patch-level and
   inside Soda's own caps, but they are not this project's to choose for a
   user who never asked for Soda.
. **Defer** until Soda lifts its caps, and revisit at the next release.
