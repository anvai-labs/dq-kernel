= SPEC-007: SQLAlchemy Core sink and Arrow fast path

:sectlinks.

== Purpose

Generalize the durable sink from PostgreSQL-specific DB-API to SQLAlchemy
Core (any RDBMS) with an optional Arrow batch-insert fast path — injected,
never imported by the framework.

== In scope

* `PostgresOutcomeSink` becomes `SqlAlchemyOutcomeSink` (Postgres alias
  retained) constructed with an injected `sqlalchemy.Engine` or
  `Connection`.
* Statements move from `%s` params to SQLAlchemy `text()` with named binds;
  identifiers use SQLAlchemy quoting where the dialect requires it —
  validated identifiers still come from `dq.identifiers`.
* Arrow fast path: bounded artifacts convert to a pyarrow table and insert
  via SQLAlchemy executemany over record dicts (pyarrow optional; fallback
  is row dicts as today).
* Retention, prune, verify_schema, namespace scoping: semantics unchanged
  from SPEC-001/006.
* Packaging: optional extras `sqlalchemy` (`>=2.0,<2.2`; the dqx extra
  requires `<2.1`, the two ranges overlap) and `arrow` (`pyarrow`).

== Out of scope

* Other RDBMS certification lanes (Postgres remains the tested lane);
* replacing the DB-API fake tests (they migrate to a fake SQLAlchemy
  engine).

== Acceptance gates

* G1 — Contract tests with a fake SQLAlchemy engine prove: quoted DDL,
  executemany insert shape, run-scope transaction lifecycle, namespace
  scoping, and prune — decision-equivalent to the DB-API path.
* G2 — A pyarrow-present test proves the Arrow conversion path; absence of
  pyarrow falls back without error.
* G3 — No psycopg/SQLAlchemy/pyarrow import at framework import time.

[NOTE]
====
Amended 2026-11-25, during implementation, from what SQLAlchemy 2.0 and
2.1 and PySpark 3.5.9 actually do.

* The tests do not use a fake SQLAlchemy engine. A recording fake cannot
  show a statement working; within minutes of meeting a real database, the
  first draft of this sink failed twice. The statements are now executed by
  SQLite -- a file-backed database with a `dq` schema attached, where they
  succeed or fail -- compiled for the PostgreSQL dialect to hold their
  certified shape, and `test_sqlalchemy_sink_postgres.py` runs them against
  a real PostgreSQL when `DQ_TEST_POSTGRES_URL` names one. No test had run
  this sink against a real PostgreSQL before.
* The database driver is needed when the sink is built. The DB-API sink
  imported psycopg at the first connection; SQLAlchemy imports the driver
  when it creates the engine. That is earlier, and it is a configuration
  fault (exit code 2) that names what to install.
* `repository { type = "postgres" }` is unchanged for existing rule packs.
  The value of `DQ_POSTGRES_DSN` is a SQLAlchemy URL. One written
  `postgresql://` means psycopg 3, as it always did for this sink, and a
  libpq keyword/value DSN is still read by psycopg 3.
* The SQL is written in forms other databases also accept: a correlated
  `EXISTS` replaces PostgreSQL's `DELETE ... USING`, and the DDL is compiled
  for the engine's own dialect. PostgreSQL remains the only certified lane.
* An artifact row is made strict JSON before it is stored. The DB-API sink
  serialized the row as it was, which wrote `NaN` -- text a `jsonb` column
  refuses, as a test on the real server shows -- and could not store a
  decimal at all.
* Classic PySpark 3.5 has no public Arrow export: `toArrow()` exists only
  in Spark Connect and PySpark 4. The fast path reads a Spark DataFrame
  through `_collect_as_arrow()` when that is what the frame offers. A first
  draft called `toArrow()`, and three tests that passed had never run
  through Arrow: both ways of reading a frame gave the same rows, so no
  test could tell. The tests now offer the sink a frame that has nothing
  but the Arrow export.
* Arrow and a frame's own rows do not spell a row alike: a timestamp
  arrives with its time zone through Arrow, and without one from
  `collect()`. The sink spells Arrow's rows as the frame's, so a stored
  payload does not depend on whether pyarrow is installed.
* `sqlalchemy >=2.0,<2.2` resolves to 2.0 with every extra installed (the
  `dqx` extra caps it below 2.1) and to 2.1 with this extra alone. The sink
  is verified on both.
